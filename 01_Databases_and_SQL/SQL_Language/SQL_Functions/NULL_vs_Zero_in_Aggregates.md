# NULL vs Zero in Aggregates

**L4 Advanced** · [↑ SQL Functions](<_index.md>)

<!-- explainer:start -->
## 📘 Lesson

> **In one line:** `NULL` means "unknown / missing", not zero — arithmetic with it yields `NULL`, aggregates *skip* it, and the NULL-handling functions (`COALESCE`, `ISNULL`, `NULLIF`) let you decide deliberately when "missing" should count as 0.

### 1. The big picture
SQL uses **three-valued logic**: a predicate is `TRUE`, `FALSE` or `UNKNOWN`. `NULL` is how a value becomes unknown. That one decision explains most "my totals are wrong" reports:

- `5 + NULL` is `NULL`, not 5.
- `NULL = NULL` is `UNKNOWN`, not true (use `IS NULL`).
- `SUM`, `AVG`, `MIN`, `MAX` and `COUNT(column)` **ignore** NULLs; only `COUNT(*)` counts rows regardless.
- An aggregate over *only* NULLs (or an empty set) returns `NULL` — except `COUNT`, which returns 0.

The *Ultimate T-SQL* book frames the practical need: if `Discount` is `NULL` for orders with no discount, `Price - Discount` is `NULL` for those orders, so net revenue silently drops them. Functions such as `ISNULL`, `COALESCE` and `NULLIF` exist to handle that explicitly. Zero is a *value* ("we know there was no discount"); NULL is the *absence* of knowledge ("we don't know / not applicable"). Which is right is a business decision, not a technical one.

### 2. Core concepts and vocabulary
- **NULL** — marker for missing/unknown/inapplicable data; belongs to no data type's value set but can appear in any nullable column.
- **Three-valued logic** — `TRUE / FALSE / UNKNOWN`. `WHERE` keeps only `TRUE` rows, so `UNKNOWN` rows are dropped.
- **NULL propagation** — arithmetic, string concatenation (in most engines) and comparisons with NULL yield NULL/UNKNOWN.
- **Aggregate function** — collapses a group of rows into one value: `COUNT`, `SUM`, `AVG`, `MIN`, `MAX`.
- **`COALESCE(a, b, …)`** — ANSI; returns the first non-NULL argument.
- **`ISNULL(a, b)`** — T-SQL; two arguments only, result type is the first argument's type.
- **`NVL`** (Oracle), **`IFNULL`** (MySQL) — two-argument equivalents.
- **`NULLIF(a, b)`** — returns NULL if `a = b`, else `a`.
- **`IS [NOT] DISTINCT FROM`** — null-safe comparison (PostgreSQL, standard SQL).
- **`GROUPING()`** — distinguishes NULLs generated by `ROLLUP`/`CUBE` subtotal rows from real NULLs.

### 3. How it works, step by step
How an aggregate processes a column `x`:

1. Take all rows in the group (after `WHERE`).
2. **Discard rows where `x` is NULL** (for every aggregate except `COUNT(*)`).
3. Apply the function to the remaining values.
4. If nothing remains → `NULL` (`COUNT` → 0).

So for values `(10, NULL, 20)`:

| Expression | Result | Why |
|---|---|---|
| `SUM(x)` | 30 | NULL skipped |
| `AVG(x)` | 15 | 30 / **2**, not 30 / 3 |
| `COUNT(x)` | 2 | counts non-NULL |
| `COUNT(*)` | 3 | counts rows |
| `MIN(x)`, `MAX(x)` | 10, 20 | NULL skipped |
| `AVG(COALESCE(x,0))` | 10 | NULL turned into 0 first, so denominator = 3 |

The `AVG` row is the important one: skipping NULL and treating it as zero give *different averages*. Neither is "right"; they answer different questions ("average of recorded values" vs "average including missing as zero").

> Note: some answer-bank text says "NULLs are treated as zeros" in `SUM`. That is wrong. They are *ignored*; the result is the same as zero only for SUM, and an all-NULL group gives NULL, not 0.

### 4. Worked example
```sql
CREATE TABLE orders (id int, price numeric(10,2), discount numeric(10,2));
INSERT INTO orders VALUES (1, 100, 10), (2, 80, NULL), (3, 50, 0);

SELECT id,
       price - discount                   AS net_naive,    -- 90, NULL, 50
       price - COALESCE(discount, 0)      AS net_ok        -- 90, 80, 50
FROM orders;

SELECT SUM(price - discount)               AS total_naive, -- 140  (order 2 silently lost)
       SUM(price - COALESCE(discount,0))   AS total_ok,    -- 220
       COUNT(*)                            AS n_rows,      -- 3
       COUNT(discount)                     AS n_discounts, -- 2  (the 0 counts; the NULL doesn't)
       AVG(discount)                       AS avg_known,   -- 5.00
       AVG(COALESCE(discount,0))           AS avg_all      -- 3.33
FROM orders;
```

Read it like this: order 2 has an *unknown* discount, so `price - discount` is unknown, and `SUM` skips it — you under-report revenue by 80 without any error. Order 3 has a *known* zero discount and is included in `COUNT(discount)`. The two averages, 5.00 vs 3.33, differ by what you declare NULL to mean.

**Divide-by-zero with `NULLIF`:**
```sql
SELECT SalesAmount / NULLIF(NumSales, 0) AS AvgSale FROM EmployeeSales;
```
When `NumSales = 0`, `NULLIF` returns NULL, so the division yields NULL instead of an error. If downstream code sums that column, combine them: `COALESCE(SalesAmount / NULLIF(NumSales, 0), 0)` — but only if "0" is a sensible fallback; otherwise leave NULL and handle it in the report.

**Subtotals vs real NULL (`ROLLUP`):**
```sql
SELECT region, product, SUM(sales) AS s,
       GROUPING(region) AS g_region, GROUPING(product) AS g_product
FROM sales GROUP BY ROLLUP (region, product);
```
`GROUPING(col) = 1` means "this NULL is a subtotal placeholder", `0` means "a real NULL in the data".

### 5. Under the hood
- **Storage.** Fixed-width columns keep a *null bitmap* per row (SQL Server) or a null bitmap in the tuple header (PostgreSQL); NULL occupies no data bytes in variable-length storage, which makes sparse columns cheap.
- **Indexes.** SQL Server, PostgreSQL and MySQL index NULLs (so `IS NULL` can seek); Oracle B-tree indexes **omit** rows where all key columns are NULL, so `WHERE col IS NULL` cannot use a single-column index there.
- **Uniqueness.** A `UNIQUE` constraint treats NULLs differently by engine: PostgreSQL and Oracle allow many; SQL Server allows only one NULL (use a filtered index to allow many); PostgreSQL 15+ has `NULLS NOT DISTINCT`.
- **Grouping and `DISTINCT`** treat NULLs as *equal* to each other (all NULLs form one group) even though `NULL = NULL` is unknown. Sorting places NULLs first or last depending on engine (`NULLS FIRST/LAST` in PostgreSQL/Oracle).
- **`COALESCE` vs `ISNULL`.** `COALESCE` is a `CASE` shorthand: result type follows data-type precedence of all arguments, and it re-evaluates arguments (subqueries inside can run twice). `ISNULL` returns the type of the first argument — `ISNULL(varchar(5)_col, 'abcdefgh')` truncates to 5 characters. `COALESCE` is standard; `ISNULL` is not (Itzik Ben-Gan prefers standard options when there's no functional difference).
- **`GREATEST` / `LEAST`.** PostgreSQL ignores NULLs (returns NULL only if all are NULL); MySQL and Oracle return NULL if any argument is NULL. This difference has bitten many migrations.

### 6. Performance and design implications
- Wrapping a column in `COALESCE(col, 0)` inside a `WHERE` makes the predicate non-sargable. Prefer `WHERE col = 0 OR col IS NULL`, or a computed/default value stored in the column.
- `COUNT(*)` vs `COUNT(col)` can silently differ: audit which one a metric *means* ("number of orders" vs "number of orders with a recorded discount").
- `NOT IN (subquery)` returns no rows if the subquery contains a NULL; use `NOT EXISTS`.
- Prefer `NOT NULL DEFAULT 0` where zero is semantically correct (counters, quantities) — then aggregates are naturally right. Keep NULL for "unknown/not applicable" (birth date, end date of open contracts).
- Conditional aggregation: `SUM(CASE WHEN status='PAID' THEN amount END)` — the missing `ELSE` returns NULL which `SUM` skips, exactly what you want; `ELSE 0` is also fine for `SUM` but changes `AVG` and `COUNT`.
- Weighted average: `SUM(value*weight) / NULLIF(SUM(weight), 0)` — handles zero total weight; rows with NULL value *or* NULL weight drop out of the numerator but not necessarily the denominator — filter both consistently.

### 7. Commands and settings you should know
| Command / setting | What it does | When to use |
|---|---|---|
| `COALESCE(a,b,…)` | First non-NULL | Defaults, portable |
| `ISNULL(a,b)` / `NVL` / `IFNULL` | Two-arg replace | Engine-specific shorthand |
| `NULLIF(a,b)` | NULL when equal | Avoid divide-by-zero, normalise sentinels ('', 'N/A', 0) |
| `IS NULL` / `IS NOT NULL` | Null test | Never use `= NULL` |
| `IS DISTINCT FROM` | Null-safe `<>` | Change detection in upserts |
| `COUNT(*)`, `COUNT(col)`, `COUNT(DISTINCT col)` | Row vs non-NULL vs distinct non-NULL | Pick deliberately |
| `GROUPING(col)`, `GROUPING_ID` | Flag subtotal NULLs | `ROLLUP` / `CUBE` reports |
| `SET ANSI_NULLS`, `CONCAT_NULL_YIELDS_NULL` (SQL Server) | Legacy null behaviors | Leave ON |

### 8. Trade-offs and decisions
| Choose this when | Avoid / watch out when |
|---|---|
| Keep NULL for unknown | Defaulting to 0 makes "unknown" look like "known zero" in averages |
| `COALESCE(x,0)` in the metric | Doing it in a `WHERE` on an indexed column |
| `NOT NULL DEFAULT 0` on counters | Columns where "not applicable" exists |
| `NULLIF(den,0)` to prevent errors | Leaving the NULL result to be summed without thinking |
| `COUNT(*)` for rows | A report that is really "customers with a value" |

### 9. Common mistakes
- `WHERE col = NULL` → always UNKNOWN, returns nothing → `IS NULL`.
- `price - discount` with NULL discounts → rows vanish from totals → `COALESCE(discount,0)`.
- Assuming `AVG` divides by row count → divides by non-NULL count → decide with `AVG(COALESCE(x,0))` if zero is intended.
- `NOT IN` with a NULL in the list → empty result → `NOT EXISTS`.
- Expecting `SUM` over an empty group to be 0 → it's NULL → `COALESCE(SUM(x),0)`.
- `NULLIF` then `SUM` → division result NULL poisons totals if mishandled → combine with `COALESCE` where zero is acceptable.
- `GROUP BY` with a selected column that isn't grouped or aggregated → error, because there is no single value per group (some engines such as old MySQL silently pick one) → group or aggregate it.

### 10. 🎯 Interview kit
**30-second answer:** "NULL is unknown, not zero. Arithmetic with it gives NULL, comparisons give UNKNOWN, and aggregates ignore NULLs — `SUM`, `AVG`, `MIN`, `MAX` and `COUNT(col)` skip them, `COUNT(*)` doesn't. I use `COALESCE` when 'missing' should count as a value and `NULLIF` to prevent divide-by-zero."

**Structure a longer answer:** define NULL & 3VL → aggregate rules with a 3-row example → show the `AVG` difference → call out `NOT IN`, unique constraint and engine differences.

**Likely follow-ups:**
- *`COUNT(*)` vs `COUNT(col)`?* → rows vs non-NULL values.
- *`COALESCE` vs `ISNULL`?* → standard, n-arg, type precedence vs T-SQL two-arg, first-arg type.
- *How do you tell a ROLLUP subtotal NULL from a real NULL?* → `GROUPING()`.
- *Weighted average edge cases?* → zero total weight (`NULLIF`), NULL weights, NULL values.
- *Why does `NOT IN` return nothing?* → a NULL makes predicate UNKNOWN for every row.
- *Cross-engine `GREATEST`?* → NULL handling differs.

**Signals interviewers look for:** you can predict results of aggregates on NULLs without running, and you pick between NULL and 0 on business meaning.
