# UUID vs Serial Keys

**L4 Advanced** · [↑ PostgreSQL Platform](<_index.md>)

<!-- explainer:start -->
## 📘 Lesson

> **In one line:** Sequential keys (`identity`/`serial`, 8 bytes) are compact, index-friendly and cheap but guessable and centrally generated, while random UUIDs (16 bytes) are globally unique and safe to generate anywhere but fragment B-tree indexes — time-ordered UUIDs (v7) give you most of both.

### 1. The big picture
Every table needs a primary key, and the first design decision is *where the value comes from*: the database (a sequence) or the client (a UUID). The choice affects index size and write speed, how rows can be merged or sharded across systems, whether ids leak information (order counts, creation rates), and how easy it is to insert a parent and children in one go.

The root of the performance difference is the B-tree. A primary key index is a B-tree whose leaf pages hold keys in sorted order. Monotonically increasing keys always insert at the rightmost leaf — hot, cached and densely packed. Random keys land anywhere, touching a random leaf each time, causing page splits, cache misses and larger write-ahead logs. Database Internals-style B-tree reading is the key here: PostgreSQL uses B-link-trees, with a "high key" in each node and right-sibling links so that concurrent splits don't block readers, but a split is still a split.

### 2. Core concepts and vocabulary
- **Surrogate key** — an artificial identifier with no business meaning (as opposed to a natural key like email).
- **Sequence** — a database object that hands out increasing numbers; backs `serial` and identity columns.
- **`serial`** — legacy shorthand: `integer` + sequence + default. **`GENERATED … AS IDENTITY`** — the standard-compliant replacement, owned by the column.
- **`bigint` vs `integer`** — 8 vs 4 bytes; 2³¹ ≈ 2.1 billion overflows sooner than people expect.
- **UUID** — 128-bit identifier, stored natively by the `uuid` type in 16 bytes (the text form is 36 characters — never store it as `varchar`).
- **UUID v4** — fully random (except version bits); `gen_random_uuid()` is built in since PG 13.
- **UUID v7** — 48-bit millisecond timestamp prefix + random bits; sortable by creation time (native generator `uuidv7()` in PG 18; extensions or app code before).
- **Index fragmentation / page split** — a full leaf page divides in two to take a new key, leaving half-full pages.
- **Fillfactor** — percentage of a page filled during build; leaves room for later inserts.
- **Enumeration attack / IDOR** — guessing sequential ids to access other users' data.

### 3. How it works, step by step
**Sequence-based key:**
1. `INSERT` omits `id`; the column default calls `nextval('seq')`.
2. The sequence lives in one small relation; each call advances it under a light lock and writes WAL only every 32 values (it logs ahead).
3. Values are *not* gapless: rollbacks, crashes and cached ranges leave holes. They are also not strictly commit-ordered across concurrent transactions.
4. The new key is greater than all existing ones, so the index entry goes to the rightmost leaf.

**Random-UUID key:**
1. The client or `gen_random_uuid()` creates 122 random bits.
2. The B-tree descends from the root to the leaf where that value belongs — essentially a random leaf.
3. If the leaf is full it splits; after warmup nearly every insert dirties a different page, and after a checkpoint the first modification of each page writes a **full-page image** to WAL, inflating WAL volume.
4. Every secondary index and every foreign key referencing the key repeats the larger 16-byte value.

| Property | `bigint` identity | UUID v4 | UUID v7 |
|---|---|---|---|
| Size in table & each index entry | 8 B | 16 B | 16 B |
| Insert locality | excellent (right edge) | poor (random) | good (time-ordered) |
| Generated by | database only | anywhere | anywhere |
| Guessable / leaks volume | yes | no | partly (creation time) |
| Merge/shard across systems | collisions | safe | safe |
| Sortable by creation | yes | no | yes |
| Human-friendly | yes | no | no |

### 4. Worked example
```sql
-- A: identity
CREATE TABLE orders_a (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id int NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);

-- B: random UUID
CREATE TABLE orders_b (
  id uuid DEFAULT gen_random_uuid() PRIMARY KEY,
  customer_id int NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);

-- Load the same number of rows into each, then compare
INSERT INTO orders_a (customer_id) SELECT g % 1000 FROM generate_series(1, 5000000) g;
INSERT INTO orders_b (customer_id) SELECT g % 1000 FROM generate_series(1, 5000000) g;

SELECT relname, pg_size_pretty(pg_relation_size(oid)) AS size
FROM pg_class WHERE relname IN ('orders_a_pkey', 'orders_b_pkey');
-- Typical result: the identity index is roughly 100 MB, the uuid index 150+ MB
-- (fill is also looser); the WAL generated during the load is visibly higher for B.

-- Check fragmentation with the pgstattuple extension
CREATE EXTENSION IF NOT EXISTS pgstattuple;
SELECT avg_leaf_density FROM pgstatindex('orders_b_pkey');   -- ~70% vs ~90% for sequential
```
Reading it: `avg_leaf_density` near 90% means pages are packed (sequential); about 65–70% reflects random-insert splits. The insert throughput difference grows once the index no longer fits in `shared_buffers`: sequential inserts keep touching the same hot pages, random ones read random pages from disk.

Practical hybrid — expose an opaque id, use a compact internal key:
```sql
CREATE TABLE users (
  id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,  -- joins, FKs
  public_id uuid   NOT NULL DEFAULT gen_random_uuid() UNIQUE, -- URLs, APIs
  email     text   NOT NULL UNIQUE
);
```

### 5. Under the hood
- **Sequence internals:** a sequence is a one-row relation (`last_value`, `log_cnt`, `is_called`). `nextval` is non-transactional by design — an aborted transaction does not give the number back — which is why sequences scale but leave gaps. `CACHE n` makes each backend reserve a range (more throughput, bigger gaps and out-of-order ids across sessions).
- **`serial` vs identity:** `serial` creates a separate sequence with a dependency; ownership/privilege and `pg_dump` handling are clumsier. `GENERATED ALWAYS` blocks accidental explicit values (needs `OVERRIDING SYSTEM VALUE`); `BY DEFAULT` allows loading data with explicit ids but then you must reset the sequence (`setval`).
- **Integer overflow:** `serial`/`integer` stops at 2 147 483 647 with an error; migrating a billion-row table's PK to `bigint` is a rewrite. Start with `bigint` unless you are certain.
- **B-tree behaviour:** PostgreSQL has a "rightmost page" optimization (fast path) for monotonic inserts, avoiding descent from the root. Random keys cannot use it. Also B-tree deduplication and index-only scans work the same, but a 16-byte key means fewer keys per 8 KB page (about 50% fewer than 8-byte), so a taller tree and more cache needed.
- **Full-page writes:** after each checkpoint, the first change to any page logs the whole 8 KB page; random keys touch many more distinct pages per checkpoint cycle than sequential ones, increasing WAL and replica traffic.
- **Time-ordered UUIDs:** v7 keeps the leading bits sorted so inserts behave like sequential ones at the page level while remaining unique without coordination; ordering across nodes is only as good as their clocks.
- **Text storage:** a `uuid` column is 16 bytes; the same value as `text` is 37 bytes in the heap and index, and compares slower.

### 6. Performance and design implications
- At small and medium scale (millions of rows, data fits in memory) the difference is minor; the penalty shows up with large tables, many secondary indexes, or write-heavy ingest.
- Every FK column and every index repeats the key: wider keys multiply index size and cache pressure across the schema.
- Use a time-ordered id (UUID v7, ULID-like, or bigint) for append-heavy tables; use v4 where unguessability is more important and volume is moderate.
- Sharding or multi-writer/multi-region designs favour UUIDs (or per-node ranges / Snowflake-style 64-bit ids) because a central sequence becomes a bottleneck or single point of failure.
- Batch inserts with parent/child keys are easier with client-generated UUIDs, no `RETURNING` round trip needed; with identities use `INSERT … RETURNING id` or a CTE.
- Don't use keys as ordering for business semantics; keep `created_at`.
- Partitioned tables need the partition key in the PK anyway, so time-ordered ids pair naturally with time partitioning.

### 7. Commands and settings you should know
| Command / setting | What it does | When to use |
|---|---|---|
| `GENERATED ALWAYS AS IDENTITY` | Standard auto-increment column | Default choice for single-DB apps |
| `serial` / `bigserial` | Legacy shorthand | Existing schemas only |
| `gen_random_uuid()` | Random v4 UUID (core since PG 13) | Opaque, unguessable ids |
| `uuidv7()` (PG 18) / extension / app library | Time-ordered UUID | Large, write-heavy tables |
| `uuid` type | 16-byte native storage | Always instead of `text` |
| `setval('seq', max+1)` | Re-sync sequence after bulk load | After explicit-id imports |
| `pgstatindex()` (pgstattuple) | Leaf density, fragmentation | Judge index health |
| `REINDEX INDEX CONCURRENTLY` | Rebuild bloated index online | Fix fragmentation |
| `CREATE SEQUENCE … CACHE n` | Reserve ranges per session | High-rate inserts |

### 8. Trade-offs and decisions
| Choose this when | Avoid / watch out when |
|---|---|
| `bigint` identity: single primary DB, joins heavy, compact indexes | Ids are exposed in URLs and must not be enumerable (add a public id) |
| UUID v4: public, unguessable ids; client-side generation; merging datasets | Huge insert-heavy tables on tight memory/IO |
| UUID v7: distributed generation *and* index locality | Id leaking creation time is a concern; clocks badly skewed |
| Composite/natural key: genuinely immutable business key | Natural key may change (email, phone) — breeds cascading updates |
| Hybrid internal bigint + public uuid | Extra column/index cost is unwelcome for tiny tables |

### 9. Common mistakes
- Using `integer`/`serial` for a growing table → hits 2.1 billion and fails → `bigint` from the start.
- Storing UUIDs as `varchar(36)` → twice the size, slower comparisons → `uuid` type.
- Assuming sequence values are gapless or commit-ordered → broken invoice numbering or "latest" logic → use a separate gapless counter (with locking) or a timestamp.
- Exposing sequential ids in URLs → enumeration/IDOR → authorization checks plus opaque public ids.
- Loading rows with explicit ids and not resetting the sequence → duplicate key errors later → `setval`.
- Choosing v4 UUID for a 10-billion-row event table → bloated, slow inserts → v7 or bigint with partitioning.
- Treating UUID as "free" for performance because of "no hot spot" claims → ignores cache misses and WAL → measure.

### 10. 🎯 Interview kit
**30-second answer:** A `bigint` identity is 8 bytes, monotonic and index-friendly, but central and guessable. A random UUID is 16 bytes, globally unique and generated anywhere, but inserts land on random B-tree pages, causing splits, bigger indexes and more WAL. For distributed generation with locality I use time-ordered UUIDs (v7), or an internal bigint plus a public UUID.

**Structure a longer answer:** clarify scale, write rate, distribution and exposure → B-tree mechanics (right-edge inserts vs random splits) → size/FK multiplication → security and sharding → pick: identity, v4, v7 or hybrid.

**Likely follow-ups:**
- *Why are sequences not gapless?* → non-transactional `nextval`, caching, rollbacks.
- *`serial` vs identity?* → identity is standard, owned by the column, safer with `ALWAYS`.
- *How do you measure the index impact?* → `pg_relation_size`, `pgstatindex`, WAL bytes, insert throughput under realistic memory.
- *Is UUID v4 ever fine?* → yes, moderate volume or when unguessability dominates.
- *How would you migrate int → bigint online?* → add bigint column, dual-write, backfill, swap, with `NOT VALID` constraints.

**Signals interviewers look for:** you tie the choice to B-tree behaviour and WAL rather than slogans, you consider exposure and distribution, and you propose a hybrid or time-ordered option.
