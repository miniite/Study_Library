# How would you cache negative results (a 'user not found') without letting an attacker flood you with junk keys?

**Difficulty:** Deep · **Levels:** Architect/Principal, Fresher, SDE-1, SDE-1/2, SDE-2/3 · [↑ Caching Expensive Queries](<../../../../07_Distributed_Systems_and_Design/System_Design/Caching/Caching_Expensive_Queries/_index.md>)

## Answer

To address caching negative results like "user not found" securely, we need to ensure that attackers cannot exploit our system by flooding it with invalid keys. This problem involves understanding caching strategies and implementing robust security measures.

Firstly, let's summarize the key aspects of this question:

We need a caching mechanism for "user not found" responses.
We must prevent an attacker from flooding the cache with junk keys to exhaust resources or cause performance degradation.
The solution should be efficient in terms of both time and space complexity.
Step-by-Step Solution
1. Choose the Right Caching Strategy

For negative results, we can use a simple key-value store like Redis for its speed and reliability. However, we need to ensure that the keys used are unique and not easily guessable by attackers.

2. Key Generation and Validation

We should generate keys in such a way that they cannot be trivially guessed or generated by an attacker. A common approach is to combine user identifiers with a timestamp or a random token. For example, if we have a user ID 12345, we could use the format:

CODE
user-{userId}-{timestamp}

This makes it difficult for attackers to predict which keys will be used and cache them.

3. Expiration Strategy

To avoid unnecessary storage of negative results, we can set an expiration time on these cache entries. For example, if a user is not found, the entry could expire after 10 minutes:

PLAINTEXT
EXPIRE user-12345-1678901234 600
4. Rate Limiting and Flood Protection

To prevent an attacker from flooding the cache with junk keys, we can implement rate limiting at multiple levels:

API Level: Use tools like AWS WAF or Azure API Management to limit requests per IP address or user.
Cache Layer: Implement a sliding window mechanism where each key can only be queried within a certain time frame (e.g., every 5 minutes). If too many invalid queries are detected, the system can dynamically increase the expiration time for that specific key.
5. Logging and Monitoring

Maintain logs of all cache operations to monitor unusual activity. This helps in early detection of potential attacks and allows for proactive mitigation measures.

#### Closing Summary

In summary, we need a combination of secure key generation, efficient caching with proper expiration strategies, rate limiting, and robust monitoring to prevent attackers from flooding our system with junk keys. By ensuring that each step is carefully designed, we can maintain the integrity and performance of our cache mechanism.

#### Common Mistakes/Follow-Ups

Failing to implement rate limiting or monitoring could lead to a denial-of-service attack.
Using predictable key formats might allow attackers to easily guess which entries are stored in the cache.
Not setting proper expiration times for negative results can lead to unnecessary storage and potential resource exhaustion.

# Example Python code for Redis caching with rate limiting

import redis
from datetime import timedelta, datetime

cache = redis.Redis(host='localhost', port=6379, db=0)

def cache_negative_result(user_id):
    key = f"user-{user_id}-{int(datetime.now().timestamp())}"

    # Check if the key has been queried recently within a sliding window
    last_queried_key = f"last-quered-{key}"
    if not cache.exists(last_queried_key):
        cache.set(key, "not found", ex=600)  # Cache for 10 minutes
        cache.expire(last_queried_key, 300)  # Ensure it's checked again in 5 minutes

    return key

def check_rate_limit(user_id):
    last_queried_key = f"last-quered-{cache_negative_result(user_id)}"
    if not cache.exists(last_queried_key):
        raise RateLimitExceeded()
