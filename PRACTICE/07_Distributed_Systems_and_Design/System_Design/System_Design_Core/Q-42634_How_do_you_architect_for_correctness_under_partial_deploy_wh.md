# How do you architect for 'correctness under partial deploy' where, during a rolling release, old and new code run simultaneously and produce events consumed by both versions? Give the design rules that prevent silent data corruption.

## Answer

In a rolling release scenario, ensuring correctness under partial deployment is critical to avoid silent data corruption where parts of your system might be running different versions of code and handling events inconsistently. The key challenge here is maintaining consistency across both old and new systems while they coexist temporarily. This requires a robust design that handles state transitions, event processing, and versioning meticulously.

The question is probing into understanding the intricacies of distributed systems and how to ensure transactional integrity when components are in different states. We need to consider assumptions like atomicity of transactions, consistency models (such as eventual consistency vs strong consistency), and handling edge cases where the system is partially updated.

To achieve this, we will follow a step-by-step design process from first principles:

Versioned Event Streaming: Ensure all events are versioned.
Event Validation and Processing: Implement validation mechanisms to ensure new code can handle old events and vice versa.
Transactional State Handling: Manage state transitions carefully to avoid data corruption.
Rollback Mechanisms: Have robust rollback plans in place if something goes wrong during the transition.

Let’s dive into these steps more deeply:

Step 1: Versioned Event Streaming

All events generated by the system should include a version identifier that specifies which version of the event schema is being used. This ensures compatibility between different versions of your codebase. For example, an event might look like this:

JSON
{
  "version": "2.0",
  "type": "UserLogin",
  "timestamp": "2023-10-05T14:30:00Z",
  "user_id": "12345"
}

This version number allows the new code to handle events from older versions while ensuring that it doesn’t incorrectly interpret newer formats.

Step 2: Event Validation and Processing

The system must validate each event before processing. This validation should check if the current version of the code can handle an incoming event, especially when old parts of the system are still running. If not, it should either log an error or wait for a compatible version to be available.

Here’s a sample function that performs this validation:

PYTHON
def validate_and_process_event(event):
    current_version = get_current_code_version()

    # Check if event version is supported by current code
    if int(event['version']) > current_version:
        log(f"Event {event} not processed due to unsupported version.")
        return

    # Process the valid event
    process_event(event)
Step 3: Transactional State Handling

When transitioning between versions, ensure that state changes are atomic and consistent. Use techniques like distributed transactions or local transactions combined with eventual consistency to manage this.

For example, if you have a user login event, the system should either fully log in the user or not at all, ensuring no partial state change occurs:

PYTHON
def handle_user_login(event):
    try:
        # Perform database operations atomically
        with db_transaction():
            update_user_session(event['user_id'])
            notify_user_of_login()

        return "Login successful"
    except Exception as e:
        log_error(e)
        return "Login failed due to internal error"
Step 4: Rollback Mechanisms

Implement rollback plans to handle situations where the transition goes wrong. This could involve rolling back changes or reverting certain states to a known good configuration.

For instance, if an event handler fails and causes data corruption:

PYTHON
def handle_event_failure(event):
    # Revert any state changes made during this transaction
    revert_user_session(event['user_id'])

    log(f"Failed to process {event}, rolling back state.")

#### Closing Summary
and Common Mistakes

To summarize, the key design rules include versioning events, validating event processing, ensuring atomic state changes, and having robust rollback mechanisms. A common mistake is neglecting backward compatibility when new code is deployed, leading to silent data corruption or service disruptions.

Always consider edge cases where different versions of your system might interact unexpectedly. For example, ensure that old parts of the system do not inadvertently process newer events in ways that could corrupt state.
