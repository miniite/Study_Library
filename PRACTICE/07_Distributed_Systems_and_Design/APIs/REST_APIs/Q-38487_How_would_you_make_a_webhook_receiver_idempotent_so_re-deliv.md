# How would you make a webhook receiver idempotent so re-delivered events do not cause duplicate processing?

**Difficulty:** Expert · **Levels:** Fresher, SDE-1, SDE-1/2, SDE-2/3 · [↑ Idempotent POST Requests](<../../../../07_Distributed_Systems_and_Design/APIs/REST_APIs/Idempotent_POST_Requests.md>)

## Answer

To ensure that a webhook receiver is idempotent, meaning it can handle duplicate event deliveries without causing repeated or redundant processing, we need to design the system with mechanisms that track and manage events in such a way that they are processed only once, even if re-delivered. This involves both server-side logic and possibly some form of external storage.

Firstly, let's break down what the webhook receiver is expected to do: it receives an event from a source (like another service or system) over HTTP POST or GET, processes the payload, and performs necessary actions such as updating a database or sending notifications. The challenge lies in ensuring that the same event isn't processed more than once when delivered multiple times.

The core idea is to implement a mechanism for tracking events so that if an event is seen again, it can be ignored without affecting the system's correctness. This could be achieved through several approaches, but one common and effective method is using a database or some form of external storage to keep track of processed event IDs or timestamps.

Here’s how we might approach this problem from first principles:

Identify Unique Event Identifiers: Each incoming webhook event should have a unique identifier (e.g., an ID generated by the source service). This could be part of the payload or an auto-generated UUID.
Store Processed Events: Use a database to store a list of processed events. For simplicity, let’s assume we’re using Redis as it provides fast lookup and is well-suited for this task due to its key-value nature.
Check Before Processing: Before processing the event, check if it has already been stored in our tracking system. If not, proceed with processing; otherwise, discard or log a message indicating that the event was seen before.

Let’s go through each of these steps in detail:

#### Triaging the Question

The question is essentially asking how to make sure a webhook receiver doesn’t reprocess events that have already been handled. The interviewer might be probing your understanding of state management, event handling, and possibly your experience with distributed systems and databases.

#### First-Principles Solution
Define Event ID: Each incoming event must come with a unique identifier (e.g., an event_id).
Database Setup: Set up a database (e.g., Redis) to store these identifiers.
Check and Process:
On receipt of the webhook, extract the event_id.
Check if this event_id is already in the tracking database.
If not, process the event normally and add its event_id to the tracking database.
If it is already there, log a message indicating that the event was seen before and do nothing.
Code Implementation

Here’s an example implementation using Python with Flask for handling webhooks and Redis for storing processed events:

PYTHON
from flask import Flask, request
import redis
import uuid

app = Flask(__name__)
r = redis.Redis(host='localhost', port=6379, db=0)

@app.route('/webhook', methods=['POST'])
def webhook():
    event_id = str(uuid.uuid4())  # Generate a unique ID for this event

    if not r.exists(event_id):
        # Process the event
        payload = request.json
        # Do something with the payload (e.g., update database, send notifications)

        # Mark this as processed
        r.set(event_id, "processed")

    return {'status': 'OK'}, 200

if __name__ == '__main__':
    app.run(debug=True)
