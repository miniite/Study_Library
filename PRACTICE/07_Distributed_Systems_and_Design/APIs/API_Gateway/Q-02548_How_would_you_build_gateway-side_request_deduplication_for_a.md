# How would you build gateway-side request deduplication for at-most-once webhook processing when the same provider sends duplicate deliveries, and where do you store dedup keys to survive gateway restarts?

**Difficulty:** Deep · **Levels:** Architect/Principal, SDE-1/2, SDE-2/3 · [↑ Response Transformation and Upstream Errors](<../../../../07_Distributed_Systems_and_Design/APIs/API_Gateway/Response_Transformation_and_Upstream_Errors/_index.md>)

## Answer

TL;DR: To implement at-most-once webhook processing with request deduplication in an API Gateway, we need a robust system that identifies and discards duplicate requests based on unique deduplication keys stored persistently. Key considerations include choosing the right storage solution for these keys to ensure they survive gateway restarts.

#### Triage
The question is probing how you would design a mechanism to handle duplicate webhook deliveries from providers, ensuring each event is processed only once despite potential delivery failures or retries by the provider. This involves implementing request deduplication logic in the API Gateway and managing persistent storage for dedup keys across gateway restarts.

First Principles:

Identify Dedup Keys: Determine unique identifiers for requests that can be used to recognize duplicates.
Storage Solution: Choose a database or storage system where these dedup keys are stored persistently.
Gateway Logic: Implement the logic in the API Gateway to check for existing keys before processing incoming requests.

Step-by-Step Solution:

Choosing Dedup Keys:

For webhooks, common choices include unique IDs generated by the provider (e.g., message ID) or a combination of timestamp and sequence number.

Storage Implementation:

Database: Use a relational database (like PostgreSQL) for structured data storage with ACID transactions to ensure reliability.
KV Store: Utilize key-value stores like Redis or DynamoDB for fast lookups and updates, which can be critical during high traffic scenarios.

Gateway Logic:

When a request arrives, extract the deduplication key from it (e.g., X-Request-ID header).
Check if this key already exists in the storage.
If the key does not exist, process the request and insert the key into storage.
If the key exists, discard or log the duplicate request.

#### Closing Summary
By implementing a robust deduplication mechanism using persistent storage, we can ensure that each webhook event is processed at most once. This involves carefully selecting unique keys, choosing an appropriate storage solution, and integrating this logic seamlessly into the API Gateway.

#### Common Mistakes/Follow-Ups

Key Selection: Failing to choose a unique enough key can lead to false positives.
Storage Reliability: Not considering high availability and resilience in storage choices can result in data loss or inconsistencies.
Performance Impact: Choosing overly complex storage solutions without sufficient testing might introduce bottlenecks.

```python
# Example of checking for a deduplication key in an API Gateway using Flask and Redis

from flask import request, jsonify
import redis

client = redis.StrictRedis(host='localhost', port=6379, db=0)

def handle_webhook():
    # Extract the unique ID from the request headers
    webhook_id = request.headers.get('X-Request-ID')

    if not webhook_id:
        return jsonify({'error': 'Missing X-Request-ID'}), 400

    # Check if the key exists in Redis
    if client.exists(webhook_id):
        return jsonify({'message': 'Duplicate request detected'}), 208

    try:
        # Process the webhook here...

        # Insert the unique ID into Redis to mark it as processed
        client.setex(webhook_id, 3600, 'processed')

        return jsonify({'status': 'Webhook processed successfully'})

    except Exception as e:
        return jsonify({'error': str(e)}), 500

# Example Flask route implementation
@app.route('/webhooks', methods=['POST'])
def process_webhook():
    return handle_webhook()
```
