# How do you architect closed-loop automation so an LLM planner's hallucinated action is caught by a deterministic validation layer before execution?

**Difficulty:** Expert · **Levels:** Architect/Principal, SDE-2/3 · [↑ Safe Closed-loop Remediation](<../../../../07_Distributed_Systems_and_Design/Software_Architecture/Closed_Loop_Automation/Safe_Closed-loop_Remediation.md>)

## Answer

#### Overview

In this scenario, we're tasked with designing a robust closed-loop automation architecture that ensures the actions proposed by a Language Model (LLM) are validated and safe before execution. The key challenge is to catch potential errors or "hallucinations" generated by the LLM during its planning phase.

#### Triaging the Question

The interviewer is probing how we ensure the integrity of decisions made by an LLM, particularly focusing on creating a deterministic validation layer that can reliably catch any missteps before they result in actual execution. This involves understanding both the nature of the LLM's outputs and the characteristics needed in our validation process.

#### Assumptions
LLM Outputs: The LLM generates action plans or commands based on input data.
Validation Layer: A deterministic layer that checks if the proposed actions are feasible, safe, and logically sound.
Execution Context: The environment where these actions will be executed (e.g., cloud infrastructure, database).
Step-by-Step Solution:

Parse LLM Output:

The first step is to extract the actionable commands from the LLM's output. This could involve a structured format like JSON or YAML.

Action Validation Framework:

Develop a validation framework that can check each action against predefined rules, such as:
Syntax correctness
Semantic consistency (e.g., logical steps)
Safety checks (e.g., preventing harmful actions)

Real-Time Monitoring & Alerting:

Implement real-time monitoring to detect any deviations or errors in the LLM's output.

Feedback Loop:

If a validation fails, provide immediate feedback to the LLM so it can refine its planning.

Execution Environment Integration:

Ensure that the validated actions are compatible with the execution environment and have minimal risk of failure during actual execution.
Detailed Architecture:
LLM Planner
Generate Action Plan
Validation Layer
Decision to Execute
Execution Environment
Error Handling

#### Closing Summary

In summary, the architecture involves parsing LLM outputs, validating them through a deterministic framework, and ensuring that only validated actions proceed to execution. This approach minimizes risks associated with incorrect or dangerous commands generated by the LLM.

#### Common Mistakes
and Follow-Ups:
Ignoring Edge Cases: Failing to account for edge cases where the LLM might generate unusual or unexpected outputs.
Over-reliance on Validation: Ensuring that validation is robust but not overly complex, which could slow down the process.
Feedback Mechanism: Not having an effective feedback loop back to the LLM can lead to repeated errors.

# Pseudo-code for action validation
def validate_action(action_plan):
    # Syntax check
    if not is_valid_syntax(action_plan):
        return False

    # Semantic consistency check
    if not is_semantically_consistent(action_plan):
        return False

    # Safety check
    if not is_safe(action_plan):
        return False

    return True

# Example input and validation
input_plan = {"action": "delete_all_data", "target": "database"}
is_valid = validate_action(input_plan)
if is_valid:
    print("Action plan is valid.")
else:
    print("Action plan has issues.")
