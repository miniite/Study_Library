# Compare Sealed Secrets vs External Secrets Operator for a 200-cluster fleet — what trade-offs drive your choice?

**Difficulty:** Deep · **Levels:** Architect/Principal, SDE-1/2, SDE-2/3 · [↑ Secrets in GitOps](<../../../../10_DevOps_and_Platform/Delivery/GitOps/Secrets_in_GitOps.md>)

## Answer

TL;DR Summary

Sealed Secrets and External Secrets Operator are both valuable tools in managing secrets within Kubernetes clusters, but their usage scenarios and underlying principles make them suitable for different use cases. Sealed Secrets is a more straightforward solution that ensures secrets are encrypted and managed centrally, while External Secrets Operator offers greater flexibility by allowing secret retrieval from external sources like AWS S3 or Google Secret Manager.

#### Triaging the Question

The question asks us to compare Sealed Secrets with External Secrets Operator for managing secrets in a 200-cluster fleet. The key points we need to address include:

Secret Management: How each tool handles secret storage and retrieval.
Security and Encryption: The methods used to protect secrets.
Scalability: The ability of these tools to handle a large number of clusters.
Integration Flexibility: Their compatibility with various external systems.
Operational Complexity: Ease of deployment and management.

#### Assumptions
We are working with a 200-cluster fleet, implying significant scale.
Both Sealed Secrets and External Secrets Operator support Kubernetes environments.
The primary focus is on secret management, particularly for high-stakes applications like authentication keys or API tokens.

#### First Principles Solution
Sealed Secrets

Key Features:

Secret Storage: Secrets are encrypted in plaintext using a key generated by the sealed-secrets CLI tool and stored as YAML files.
Encryption Methodology: Uses TLS/1.2+ to encrypt secrets with a master key, which can be managed via KMS or a similar system.
Decryption Mechanism: Secrets are decrypted at runtime using a controller that is part of the sealed-secrets toolchain.

#### Pros

Simplicity and Centralized Management: Easy to use and manage secrets centrally without complex integrations.
Flexibility in Secret Sources: Can handle static or dynamically generated secrets.
Community Support: Well-maintained with a strong community backing.

#### Cons

Complexity in Deployment: Requires additional deployment steps for the sealed-secrets controller to decrypt secrets at runtime.
Security Concerns: If the master key is compromised, all secrets are potentially accessible.
External Secrets Operator

Key Features:

Secret Retrieval Mechanism: Allows retrieval of secrets from external sources like AWS S3, Google Secret Manager, Azure Key Vault, etc., via CRDs (Custom Resource Definitions).
Dynamic Secrets Management: Supports dynamic secret generation and rotation.
Decoupling Security and App Logic: Keeps sensitive information outside the application’s codebase, enhancing security posture.

#### Pros

Enhanced Security: Decouples secret storage from the application logic, reducing risk of exposure.
Scalability and Flexibility: Highly scalable as it can integrate with a variety of external systems for secure secrets management.
Operational Simplicity: No need to manage decryption keys within Kubernetes; leverages cloud providers' native security features.

#### Cons

Complexity in Setup: Requires setting up CRDs, permissions, and integrations with external secret stores.
Dependency on External Systems: Reliance on availability of external services for secret management.

#### Conclusion

For a 200-cluster fleet, the choice between Sealed Secrets and External Secrets Operator depends on specific requirements:

If you prioritize simplicity and centralized management while having a smaller number of secrets that don't require frequent updates or external integration, Sealed Secrets would be a suitable choice.
For scenarios where robust security measures are paramount, External Secrets Operator provides a more secure and flexible solution by leveraging cloud-native services for secret storage and retrieval.

#### Common Mistakes
and Follow-Ups
Overlooking Security: Failing to consider the security implications of storing secrets within Kubernetes or relying on external services.
Neglecting Scalability: Assuming that Sealed Secrets can handle the same number of clusters as External Secrets Operator without additional effort.
Ignoring Complexity: Underestimating the setup and operational complexity required for External Secrets Operator.

#### Closing Summary

Both tools have their merits, but the choice ultimately depends on your specific needs regarding security, scalability, and operational simplicity. Careful consideration should be given to the trade-offs before making a decision.
