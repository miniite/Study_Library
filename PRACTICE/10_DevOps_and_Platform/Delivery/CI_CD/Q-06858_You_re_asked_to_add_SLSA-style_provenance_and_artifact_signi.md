# You're asked to add SLSA-style provenance and artifact signing; what threats does each address, and how do you verify signatures at deploy time without slowing the pipeline?

**Difficulty:** Expert · **Levels:** Architect/Principal, SDE-1/2, SDE-2/3 · [↑ Supply Chain Security and Provenance](<../../../../10_DevOps_and_Platform/Delivery/CI_CD/Secrets_in_Pipelines/Supply_Chain_Security_and_Provenance.md>)

## Answer

TL;DR:

Adding SLSA (Software Bill of Materials) style provenance and artifact signing to a CI/CD pipeline enhances security by providing verifiable trust in software components. Provenance tracks where code comes from, while signatures ensure that the code has not been tampered with. Verifying these at deploy time is crucial for maintaining secure pipelines without significant delays.

#### Triaging the Question

The question asks about adding SLSA-style provenance and artifact signing to a CI/CD pipeline, specifically focusing on the threats each addresses and how to verify signatures efficiently. The goal is to ensure that both security and performance are maintained in the deployment process.

Key Assumptions:
We're dealing with a cloud-native environment using modern CI/CD practices.
SLSA stands for Software Supply Chain Security Guidance, which includes provenance (track where code comes from) and integrity checks (verify signatures).
Step-by-Step Solution:

Provenance:

Threats Addressed: Provenance helps address the issue of "Supply Chain Attacks." Malicious actors can inject malware into legitimate repositories or distributions, leading to undetected vulnerabilities.

#### Implementation
Approach: Use tools like BuildKit or Slsa4Gradle to generate a Software Bill of Materials (SBOM), which details the components and their provenance. This SBOM can be stored in a secure registry or database.

Artifact Signing:

Threats Addressed: Artifact signing ensures that only trusted parties have the authority to modify code, preventing unauthorized changes during the pipeline.

#### Implementation
Approach: Use cryptographic signatures generated by the build system (e.g., gpg for Linux-based systems). The signed artifacts should be stored alongside their corresponding SBOM.

Verification at Deploy Time:

#### Approach
During deployment, verify both the SBOM and the artifact signature.
SBOM Verification: Check if the SBOM is up-to-date and matches known good versions in a secure registry or database.
Signature Verification: Use public keys to validate the signatures on the artifacts. This can be done by integrating tools like gpg or openssl into your CI/CD pipeline.

Efficient Implementation:

Pre-Verification Phase: During the pre-build phase, verify that the SBOM and signatures are present and valid before proceeding.
Parallel Verification: To avoid slowing down the pipeline, parallelize signature verification tasks across multiple nodes or threads if possible.
Caching Mechanisms: Cache verified artifacts to reduce redundant checks in subsequent pipelines.

Security Best Practices:

Key Management: Securely store and manage private keys used for signing.
Regular Audits: Periodically audit the SBOMs and signature verification processes to ensure they remain effective against evolving threats.

#### Closing Summary

By implementing SLSA-style provenance and artifact signing, we can significantly enhance the security of our CI/CD pipeline. Provenance ensures that we know exactly where code comes from, while signatures prevent unauthorized modifications. Efficient verification strategies can be employed to maintain performance without compromising security.

#### Common Mistakes/Follow-Ups
Ignoring Key Management: Failing to securely manage private keys can lead to vulnerabilities.
Inadequate Caching: Not caching verified artifacts can slow down the pipeline unnecessarily.
Overzealous Verification: Over-verifying every artifact can introduce delays; finding a balance is key.

```python
# Example of signing and verifying an artifact in Python
import hashlib
from cryptography.hazmat.primitives import serialization, hashes
from cryptography.hazmat.primitives.asymmetric import padding

def sign_artifact(artifact_path, private_key_path):
    with open(private_key_path, "rb") as key_file:
        private_key = serialization.load_pem_private_key(
            key_file.read(),
            password=None,
        )

    with open(artifact_path, "rb") as artifact_file:
        artifact_data = artifact_file.read()

    signature = private_key.sign(
        artifact_data,
        padding.PSS(
            mgf=padding.MGF1(hashes.SHA256()),
            salt_length=padding.PSS.MAX_LENGTH
        ),
        hashes.SHA256()
    )
    return signature

def verify_artifact(artifact_path, public_key_path, expected_signature):
    with open(public_key_path, "rb") as key_file:
        public_key = serialization.load_pem_public_key(
            key_file.read(),
        )

    with open(artifact_path, "rb") as artifact_file:
        artifact_data = artifact_file.read()

    try:
        public_key.verify(
            expected_signature,
            artifact_data,
            padding.PSS(
                mgf=padding.MGF1(hashes.SHA256()),
                salt_length=padding.PSS.MAX_LENGTH
            ),
            hashes.SHA256()
        )
        return True
    except Exception as e:
        print(f"Verification failed: {e}")
        return False
```
