# A staff engineer proposes generating pipeline YAML and deploy manifests with an LLM agent to cut boilerplate across 400 services; as the accountable architect, what guardrails, provenance, and review model would you demand before letting AI-authored config touch prod, and where would you refuse it entirely?

**Difficulty:** Expert · **Levels:** Architect/Principal, SDE-2/3 · [↑ Test Data Governance](<../../../../10_DevOps_and_Platform/Delivery/CI_CD/Validating_Pipeline_Changes/Test_Data_Governance.md>)

## Answer

TL;DR

Before allowing an LLM agent to generate pipeline YAML and deploy manifests for 400 services in production, we need robust guardrails, comprehensive review processes, and provenance tracking to ensure reliability and security. Guardrails include strict validation checks, environment-specific permissions, and regular audits. We should also establish a clear review model involving human engineers and incorporate static analysis tools.

#### Triaging the Question

The question revolves around evaluating whether to use an AI-generated configuration in production for CI/CD pipelines. The core elements being probed are:

Security and Reliability: Ensuring that generated configurations do not introduce vulnerabilities or errors.
Provenance Tracking: Maintaining a clear audit trail of how, when, and who approved the changes.
Review Processes: Implementing checks to ensure human oversight and collaboration.

#### Assumptions
The pipeline contains multiple services (400+).
The LLM agent is expected to reduce boilerplate and save time.
There are existing CI/CD processes in place, but we need to enhance them with AI-generated configurations.

#### First Principles Solution
1. Guardrails
Static Validation: Implement strict validation checks using tools like Kubernetes's kubeval, which can validate manifests against a schema or best practices.
Environment-Specific Permissions: Ensure that the LLM agent has limited permissions to only generate configurations for certain environments (e.g., development, staging) and not directly prod. Use service accounts with minimal privileges.
Regular Audits: Conduct regular audits of generated configurations using tools like git diff or custom scripts to ensure no unintended changes are made.
2. Provenance Tracking
Version Control Integration: Integrate the LLM-generated YAML into Git repositories, maintaining a clear history and commit messages that reflect the AI's contributions.
Metadata Tags: Add metadata tags in comments or YAML files indicating the source (AI-generated) and timestamp of each change. This helps trace back changes if issues arise.
Audit Logs: Maintain logs for all interactions with the LLM agent, including input prompts, outputs, and final decisions.
3. Review Processes
Automated Static Analysis: Use CI/CD pipelines to run static analysis tools like KubeLinter or Yamllint before merging changes into production.
Human Review: Ensure that any code generated by the LLM agent is reviewed by at least one human engineer. This review should focus on compliance with organizational standards and security best practices.
Multi-Level Approval: Implement multi-level approval processes where a configuration change must be approved by multiple stakeholders before deploying to prod.
4. Refusal Criteria
High-Risk Services: Refuse AI-generated configurations for critical services that have high impact or risk in production. These include services handling sensitive data, security-critical components, and those with complex dependencies.
Critical Operations: Avoid using AI-generated configurations during peak operational periods to mitigate risks associated with unexpected changes.

#### Closing Summary

In conclusion, while the use of an LLM agent can significantly reduce boilerplate and streamline CI/CD processes, it is crucial to implement robust guardrails, provenance tracking, and rigorous review models. This ensures that generated configurations are secure, reliable, and maintainable. The refusal criteria help prioritize risk management by identifying services that should not be touched by AI-generated changes.

#### Common Mistakes/Follow-Ups
Overreliance on Automation: Overly trusting the LLM agent without adequate human review can lead to critical errors.
Insufficient Logging: Lack of detailed logs and metadata can make it difficult to trace back issues when they arise.
Neglecting High-Risk Areas: Failing to apply stringent controls around high-risk services can result in security vulnerabilities or service disruptions.
