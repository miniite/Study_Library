# Your Prisma/TypeORM migration succeeded in staging but locked prod; how do you review generated migration SQL for dangerous locks before it ships?

**Difficulty:** Deep · **Levels:** SDE-1/2, SDE-2/3 · [↑ Safe Migrations on Rolling Deploys](<../../../../TOOLS/PostgreSQL/PostgreSQL_Platform/Safe_Migrations_on_Rolling_Deploys.md>)

> ⚠️ Practice answer, not verified. Some answers contain mistakes; when in doubt, follow the lesson.

## Answer

To ensure that a PostgreSQL migration, as generated by tools like Prisma or TypeORM, does not lock production databases during deployment, we need to carefully inspect and test the migration scripts. Here’s a step-by-step process from first principles to understand and address potential issues:

#### Overview
When migrating databases, especially in a production environment, it's crucial to ensure that any generated SQL does not inadvertently cause table locks or other blocking operations. This can be achieved by reviewing the generated SQL directly before applying it to prod.

#### Triage
The question is essentially asking how to thoroughly review and test migration scripts for potential issues like table locking in a staging environment, ensuring they are safe for production deployment.

#### Assumptions

You have access to both a staging and production database.
Prisma or TypeORM has generated the SQL script as part of your migration process.
You need to ensure that the migration does not cause blocking issues in prod, such as table locks.

#### First-Principles Solution

Review Generated SQL: Carefully examine each SQL command to identify any potential risks, such as ALTER TABLE statements or large data migrations.
Staging Environment Test: Deploy the migration to a staging environment that mirrors your production setup as closely as possible. Use tools like pgBadger, PostgresStat, or custom scripts to monitor and log table locks and other blocking issues during the migration process.
Manual Inspection: Manually inspect the generated SQL for any operations that might cause blocking, such as large data modifications, foreign key constraint additions, or complex schema changes.
Automated Testing Frameworks: Utilize automated testing frameworks like pg-migrate to run predefined test cases on your staging database before applying the migration to prod.

#### Closing Summary
and Common Mistakes/Follow-Ups:

Always ensure that any generated SQL is thoroughly reviewed for potential blocking issues.
Use monitoring tools in the staging environment to detect and mitigate risks early.
Automate testing as much as possible to catch issues before they affect production.

**Comparison:**

| Migration Command | Potential Risk           | Mitigation Strategy       |
|--------------------|--------------------------|--------------------------|
| `ALTER TABLE`      | Table lock               | Use small transactions   |
| `INSERT INTO`      | Large data load          | Split into smaller chunks|
| `DROP COLUMN`      | Data loss risk           | Back up before applying  |

```typescript
import { PrismaClient } from '@prisma/client';
const prisma = new PrismaClient();

async function testMigration() {
  await prisma.$transaction(async (tx) => {
    // Run your custom test cases here
    const result = await tx.yourCustomModel.create({
      data: { field1: 'value1', field2: 'value2' },
    });

    console.log(`Test passed with new record ID ${result.id}`);
  });
}

testMigration().catch(e => {
  console.error(e);
  process.exit(1);
});
```
