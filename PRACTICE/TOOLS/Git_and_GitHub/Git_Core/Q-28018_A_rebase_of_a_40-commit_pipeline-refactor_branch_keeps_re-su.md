# A rebase of a 40-commit pipeline-refactor branch keeps re-surfacing the same conflict on a generated schema.yml every commit. Diagnose why, and decide between rerere, a merge driver that regenerates the file, or squashing before the rebase.

**Difficulty:** Deep · **Levels:** SDE-1/2, SDE-2/3 · [↑ Rerere and Repeated Conflicts](<../../../../TOOLS/Git_and_GitHub/Git_Core/Rerere_and_Repeated_Conflicts.md>)

## Answer

When you encounter persistent conflicts during a Git rebase, especially with files like schema.yml generated by scripts, it’s crucial to understand why these conflicts are occurring and how to resolve them effectively. This scenario involves multiple factors including the nature of the conflict, the Git features at play (like rerere), and the potential benefits of using alternative strategies such as a merge driver or squashing.

#### Triage

The core issue here is that a 40-commit pipeline-refactor branch is causing repeated conflicts with schema.yml. The key questions are:

Why is this conflict recurring?
What are the trade-offs between rerere, a merge driver, and squashing?

#### Assumptions
You have a schema.yml file that is automatically generated by scripts.
The conflict occurs during every commit in your rebase process.
Diagnosis

The repeated conflicts suggest that the schema.yml file is being modified in a way that cannot be easily resolved without an external tool or manual intervention. Here’s how to diagnose and resolve this issue step-by-step:

Understand the Conflict:

Check the conflict markers (<<<<<<<, =======, >>>>>>>) to see what parts of the file are causing issues.
Identify if the conflict is due to the nature of changes or the way these scripts regenerate the schema.

Use git rerere:

Git’s rerere feature can help remember how you resolved conflicts in previous rebases, which might prevent them from reoccurring.
However, if your conflict is too complex for rerere, it may not be effective.

Implement a Custom Merge Driver:

A custom merge driver could be used to regenerate the schema.yml file whenever conflicts arise during the rebase process.
This approach ensures that the file always ends up in a consistent state, but it might introduce overhead and complexity into your Git workflow.

Squash Commits Before Rebase:

Squashing commits before rebasing can sometimes simplify the conflict resolution by reducing the number of changes to review and merge.
However, this approach loses some granularity of individual commit history, which may be important for traceability or other reasons.

#### First-Principles Solution

Given the complexity of the schema.yml regeneration process, a custom merge driver might offer the best balance between maintaining file consistency and reducing conflict resolution overhead. Here’s how to implement it:

Create a Merge Driver:

BASH
[merge "custom_schema"]
name = Custom Schema Merge
pathspec = schema.yml

[mergetool "custom_schema"]
cmd = python /path/to/your/schema_regeneration_script.py $BASE $LOCAL $REMOTE

Update Git Configuration:

BASH
git config --global merge.custom_schema.name "Custom Schema Merge"
git config --global mergetool.custom_schema.path /path/to/your/schema_regeneration_script.py

Dry-Run the Setup:

Test the setup with a simple rebase to ensure it works as expected.
BASH
git rebase --merge <branch>
Observe if the custom merge driver is triggered and resolves conflicts effectively.

Choosing rerere: It’s useful for repetitive conflicts but might not handle complex schema changes.
