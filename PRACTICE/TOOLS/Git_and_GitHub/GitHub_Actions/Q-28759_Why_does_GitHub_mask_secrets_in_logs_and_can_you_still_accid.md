# Why does GitHub mask secrets in logs and can you still accidentally leak one?

**Difficulty:** Deep · **Levels:** Fresher, SDE-1/2, SDE-2/3 · [↑ Secrets in Actions](<../../../../TOOLS/Git_and_GitHub/GitHub_Actions/Secrets_in_Actions.md>)

## Answer

TL;DR

GitHub masks secrets in logs to protect sensitive information, but this doesn’t mean it’s impossible to inadvertently expose them. I'll explain why GitHub masks secrets, discuss how they can still be leaked, and provide some best practices to prevent accidental exposure.

#### Triaging the Question

The core of this question is twofold:

Understanding Masking in Logs: Why does GitHub mask secrets in logs?
Accidental Leak Risk: How can one still inadvertently expose a secret even with masking?

#### Assumptions
and Context
We are discussing GitHub Actions, which are workflows that run code.
Secrets are sensitive information like API keys, database passwords, etc., that need to be protected.

#### First Principles Solution
Why Does GitHub Mask Secrets in Logs?

GitHub masks secrets to protect sensitive data from unauthorized access. When a secret is used within an Action, it's replaced with asterisks (*) or other placeholders in the logs. This ensures that even if someone manages to view the logs, they won't see the actual value of the secret.

How Can Secrets Still Be Leaked?

Despite masking, there are still ways secrets can be inadvertently exposed:

Raw Access via Actions Logs:

If a log is saved or exported (e.g., in raw text format), the secret might still appear.

Logs Retention: GitHub retains logs for 30 days by default, and if an attacker gains access to these logs after they have been masked, they could potentially retrieve the original secrets.

Environment Variables in Code:

If a secret is used directly in code or scripts that are committed to the repository, it can be exposed through git blame or other tools.

CI/CD Pipeline Configuration Files:

Secrets stored in configuration files (like .env or specific sections of CI/CD pipelines) might not be masked if they are part of a pull request review.

External Tools and Services:

If the secret is used in an external tool or service, and that tool logs sensitive information, it can still expose the secret.

Logs from Other Sources:

Logs generated by other services (like AWS CloudWatch) might not be masked if they are aggregated into GitHub Actions logs.
Detailed Example

Suppose you have a GitHub Action that uses an API key stored as a secret in your repository:

YAML
name: Deploy App

on:
  push:
    branches: [ main ]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        run: git checkout main

      - name: Use API Key (masked)
        env:
          API_KEY: ${{ secrets.API_KEY }}
        run: curl https://api.example.com --header "Authorization: Bearer ${API_KEY}"

In the logs, you would see something like:

PLAINTEXT
curl https://api.example.com --header "Authorization: Bearer *************"

However, if an attacker gains access to your repository and retrieves the commit history or uses git blame, they might find the secret.

Best Practices to Prevent Accidental Exposure
Use Environment Variables:
Ensure all secrets are stored as environment variables in GitHub Actions.
Mask Secrets Properly:
Use secrets for sensitive information and avoid hardcoding them in your code or scripts.
Review Commit History:
Regularly review the commit history to ensure no secrets have been accidentally committed.
Use External Secrets Management Tools:

#### Cons
ider using external tools like HashiCorp Vault, AWS Secrets Manager, or Azure Key Vault to manage secrets securely.
Configure Retention Policies:
Adjust log retention policies on GitHub to minimize the risk of accidental exposure.

#### Closing Summary

GitHub masks secrets in logs as a security measure, but this doesn’t guarantee complete protection against accidental leaks. It's crucial to follow best practices and regularly audit your codebase to prevent secrets from being exposed.

#### Common Mistakes
and Follow-Ups
Failing to Use Environment Variables: Hardcoding secrets directly into scripts or configuration files can easily lead to leaks.
Improper Git Commit Practices: Accidentally committing sensitive information without proper checks can expose secrets.
Insufficient Review Processes: Lack of thorough code reviews and logging policies might allow secrets to slip through.
