# How do you propagate a Terraform plan artifact from a plan job to an apply job while ensuring the applied plan is exactly the reviewed one?

**Difficulty:** Expert · **Levels:** SDE-1/2, SDE-2/3 · [↑ Pinning Third-party Actions](<../../../../TOOLS/Git_and_GitHub/GitHub_Actions/Pinning_Third-party_Actions.md>)

> ⚠️ Practice answer, not verified. Some answers contain mistakes; when in doubt, follow the lesson.

## Answer

In this scenario, we need to ensure that the apply job in GitHub Actions uses the exact Terraform plan generated by the plan job. This involves a few key steps: setting up the environment correctly, using actions to handle artifacts, and ensuring version control and reproducibility.

#### Triage

The question is asking how to pass a Terraform plan artifact from one job (the plan job) to another job (the apply job) in GitHub Actions. The goal is to ensure that the apply job uses the exact same plan that was reviewed, thereby maintaining consistency and reliability.

#### Assumptions
We are using a monorepo with multiple jobs in GitHub Actions.
Terraform plans will be generated as artifacts from the plan job.
The apply job should use these artifacts to ensure it is applying the exact plan that was reviewed.

#### First-Principles Solution

To achieve this, we need to:

Configure the plan job to generate a Terraform plan and save it as an artifact.
Reference the artifact in the apply job so that it uses the same plan for execution.
Ensure both jobs are run sequentially or in a controlled manner.
Step-by-Step Solution

Plan Job Configuration:

Create a GitHub Actions workflow file (plan.yml) to generate the Terraform plan and save it as an artifact.
YAML
name: Plan Terraform

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

jobs:
  plan:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout code
        uses: actions/checkout@v2

      - name: Setup Terraform
        uses: hashicorp/setup-terraform@v1

      - name: Initialize Terraform
        run: terraform init

      - name: Plan the Terraform configuration
        id: plan
        run: terraform plan -out=tfplan

      - name: Archive artifacts
        if: steps.plan.outputs.out == 'tfplan'
        uses: actions/upload-artifact@v2
        with:
          name: tf-plan
          path: ./tfplan

Apply Job Configuration:

Create a second workflow file (apply.yml) to apply the Terraform configuration using the artifact from the plan job.
YAML
name: Apply Terraform

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

jobs:
  apply:
    runs-on: ubuntu-latest
    needs: plan  # Ensure this job depends on the plan job

    steps:
      - name: Checkout code
        uses: actions/checkout@v2

      - name: Setup Terraform
        uses: hashicorp/setup-terraform@v1

      - name: Download artifact
        uses: actions/download-artifact@v2
        with:
          name: tf-plan
          path: .

      - name: Apply the Terraform plan
        run: terraform apply -auto-approve ./tfplan

Sequence of Events:

When a push or pull request is detected, both plan.yml and apply.yml will be triggered.
The plan job generates a tfplan file and saves it as an artifact.
The apply job depends on the plan job, so it will only run after the plan has been generated.
The apply job downloads the tfplan file and applies it to the infrastructure.

#### Closing Summary

By configuring GitHub Actions in this way, we ensure that the apply job uses the exact same Terraform plan that was reviewed. This approach enhances reproducibility and maintains consistency between the planned and applied states of your infrastructure.

#### Common Mistakes/Follow-Ups
Mistake: Forgetting to define dependencies between jobs.

#### Follow-Up
Ensure both apply and plan jobs are configured with needs: plan in apply.yml.
Mistake: Not setting up the artifact correctly.

#### Follow-Up
Double-check the artifact upload step in plan.yml.
Mistake: Not triggering the correct workflow.

#### Follow-Up
Verify that both workflows are set to trigger on push and pull requests.
