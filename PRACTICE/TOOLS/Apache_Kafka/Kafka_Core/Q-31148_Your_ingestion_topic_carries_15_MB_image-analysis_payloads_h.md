# Your ingestion topic carries 15 MB image-analysis payloads; how would you use a claim-check pattern with object storage and handle orphan cleanup when a record is never consumed?

**Difficulty:** Deep · **Levels:** Architect/Principal, SDE-1/2, SDE-2/3 · [↑ Claim Check Pattern](<../../../../TOOLS/Apache_Kafka/Kafka_Core/Claim_Check_Pattern.md>)

> ⚠️ Practice answer, not verified. Some answers contain mistakes; when in doubt, follow the lesson.

## Answer

To tackle this problem, we need to ensure that we can reliably store and manage 15 MB image-analysis payloads ingested into our Kafka topic while implementing a claim-check pattern alongside object storage. This involves handling cases where records are never consumed, which leads us to the concept of orphan cleanup.

#### Triage

The core question here is how to design a robust system that efficiently handles large data payloads stored in Kafka and managed through an object storage service like AWS S3 or Google Cloud Storage (GCS). The claim-check pattern will be used to maintain references between Kafka offsets and object storage URIs, ensuring that each message can be uniquely identified and the associated file can be retrieved. Additionally, we need a strategy for handling orphan files—those created in object storage but never consumed by the processing system.

#### First-Principles Solution

Claim-Check Pattern Implementation:

Claim Check Generation: For each ingested message (payload), generate a unique claim check that serves as an identifier.
Kafka Offset Storage: Store the Kafka offset and S3 URI in an external storage system, like AWS DynamoDB or a relational database. This ensures that both the message data and its metadata are stored reliably.

Orphan File Handling:

Monitoring and Retention Policies: Implement monitoring to track which claim checks have been consumed and those that haven’t.
Orphan Cleanup Strategy: Periodically clean up orphan files by checking against the claim check database, removing entries from object storage if they are not referenced.

Error Handling and Dead Letter Queues (DLQ):

Introduce a DLQ to handle messages that fail processing, allowing them to be retried or manually inspected.
Ensure robust error logging and reporting mechanisms are in place for both Kafka and the object storage system.
Detailed Solution

Claim Check Generation:

Use Kafka’s message headers to store the claim check generated by a unique ID generator service. This can be an external microservice that generates UUIDs or other unique identifiers.

Kafka Offset and S3 URI Storage:

After ingesting each payload into Kafka, create an entry in the claim check database with the following fields:
kafka_offset: The offset of the message in the Kafka topic.
s3_uri: The URL of the stored image file in object storage.
claim_check_id: The unique identifier for this record.
SQL
CREATE TABLE claims (
    id UUID PRIMARY KEY,
    kafka_offset VARCHAR(255),
    s3_uri TEXT,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

Orphan Cleanup Strategy:

Schedule a periodic cleanup job that queries the claims table to find entries where the kafka_offset is not referenced in Kafka’s offsets.
For these orphaned records, delete the corresponding files from object storage.

Error Handling and Dead Letter Queues (DLQ):

Configure Kafka to use a DLQ for messages that fail processing. This ensures that such messages can be manually inspected or retried if necessary.
Implement retries with backoff strategies in your consumer logic to handle transient errors gracefully.

#### Closing Summary

Implementing the claim-check pattern alongside object storage and handling orphan cleanup effectively requires a well-architected system that addresses both data management and error resilience. By using external databases for storing offsets and S3 URIs, we can ensure reliable tracking of each message. The periodic cleanup job is crucial to maintaining the cleanliness of our object storage while avoiding wastage.

#### Common Mistakes
and Follow-Ups
Lack of External Metadata Storage: Not using an external database or another system to store Kafka offsets and S3 URIs can lead to data loss if Kafka fails.
Insufficient Error Handling: Failing to implement robust error handling and DLQs can result in undetected failures, leading to orphaned files.
Inadequate Cleanup Mechanism: Not having a periodic cleanup job can lead to unnecessary storage costs and potential security risks from unused data lingering.
