# What happens if you query a vector store with embeddings from a different model than was used to index, in a FastAPI app?

**Difficulty:** Deep · **Levels:** Fresher, SDE-1/2, SDE-2/3 · [↑ Model Consistency Across Deploys](<../../../../TOOLS/Python/FastAPI/Model_Consistency_Across_Deploys.md>)

## Answer

When querying a vector store using embeddings generated by a model that differs from the one used during indexing, several factors come into play. In a FastAPI application, this scenario can introduce inconsistencies and performance issues. The root of the problem lies in the differences between the embedding models—each model may have distinct ways of encoding inputs, leading to potential mismatch or degradation in retrieval accuracy.

#### Triage
What is Being Probed

The question probes your understanding of vector store consistency, model interoperability, and FastAPI application behavior under varying conditions. The interviewer might be interested in how you handle edge cases, the impact on performance, and potential solutions to mitigate issues.

#### Assumptions
Assume we are using a vector store like Pinecone or Weaviate.
Assume embeddings from two different models (Model A and Model B) are being compared.
Assume the FastAPI app is set up with endpoints for querying the vector store.

#### First-Principles Solution
Step 1: Embedding Generation

When querying a vector store, the process typically involves:

Request Reception: The FastAPI application receives a query request containing input text.
Embedding Generation: The app generates embeddings using Model A (the one used during indexing).
Vector Store Query: The generated embedding is then queried against the vector store to retrieve relevant vectors.
Step 2: Impact of Different Models

If the model used for querying (Model B) differs from the indexing model (Model A), several issues can arise:

Embedding Mismatch: Model A and Model B might have different encoding strategies, leading to embedding differences.
Retrieval Inconsistency: The vector store's embeddings are optimized for Model A’s output, making direct comparison with Model B less reliable.
Step 3: Potential Issues
Reduced Retrieval Accuracy: Queries may return irrelevant results due to the mismatch in encoding strategies.
Performance Degradation: Additional processing might be required to normalize or transform embeddings before querying the vector store.

#### Implementation
Complexity: The FastAPI application needs robust handling of different models, possibly involving custom preprocessing.
Step 4: Mitigation Strategies

To address these issues, consider implementing the following strategies:

Normalization and Transformation: Implement a normalization layer that can adapt Model B’s embeddings to be compatible with Model A.
Cross-Model Testing: Regularly test the application with different models to ensure consistency and performance.
Custom Endpoints: Develop custom endpoints in FastAPI to handle model-specific queries efficiently.
Step 5: Implementation Example

Here is a simplified example of how you might set up FastAPI for handling such scenarios:
