# How would you profile and read the actual SQL EF Core generates, and how do you catch an accidental client-side evaluation?

**Difficulty:** Deep · **Levels:** Fresher, SDE-1, SDE-1/2, SDE-2/3 · [↑ Entity Framework Core Performance](<../../../../TOOLS/DotNet/DotNet_Platform/Entity_Framework_Core_Performance.md>)

> ⚠️ Practice answer, not verified. Some answers contain mistakes; when in doubt, follow the lesson.

## Answer

To effectively profile and understand the actual SQL Entity Framework Core (EF Core) generates, we need to delve into both runtime diagnostics and query optimization. This task requires a deep understanding of EF Core's behavior, as well as knowledge of .NET profiling tools. The main goal is to ensure that client-side evaluations are minimized, which can lead to performance issues or unexpected behavior.

Firstly, let’s break down the question: we need to explore how to capture and analyze SQL queries generated by EF Core during runtime. This involves understanding the process of query generation and execution in EF Core. The key challenge here is identifying when a query might be evaluated on the client side instead of being sent directly to the database. Such evaluations can occur due to lazy loading, explicit materialization, or incorrect use of Include and Select methods.

#### Triaging the Question

The question is essentially asking us to:

Identify how to capture the SQL queries generated by EF Core.
Determine when these queries are evaluated on the client side instead of at the database level.
Implement strategies to minimize or prevent such evaluations.

#### Assumptions
and Context
We assume a .NET backend application using Entity Framework Core as the ORM.
The goal is to optimize database interactions for performance, reducing unnecessary client-side computation.
Common scenarios include lazy loading, explicit materialization, and incorrect query shaping.

#### First-Principles Solution

Setting Up SQL Logging:

EF Core provides a DbContext extension method called Log which can be used to log the SQL queries generated by the database context.
CSHARP
using (var db = new MyContext())
{
    db.Database.Log = Console.WriteLine;
    // Your database operations here
}
Alternatively, you can configure this in the appsettings.json file:
JSON
"Logging": {
    "LogLevel": {
        "Default": "Information",
        "System": "Information",
        "Microsoft": "Information"
    },
    "IncludeScopes": true,
    "EFCore": {
        "Database": "Information"
    }
}

Using Query Profiling Tools:

Tools like SQL Server Profiler, or integrated tools in Visual Studio such as the Data Explorer can be used to monitor and analyze database queries.
For .NET applications running on Azure App Services, you can use Application Insights to capture SQL query details.

Identifying Client-Side Evaluations:

Lazy Loading: EF Core uses lazy loading by default, where related entities are loaded only when accessed. This is generally efficient but can be a bottleneck if not managed properly.
CSHARP
var customer = context.Customers.Include(c => c.Orders).FirstOrDefault(c => c.CustomerId == 1);
// Here, Orders will be loaded separately from the database.
Explicit Materialization: Using ToList() or ToArray() forces execution of a query and can be expensive if not needed.
CSHARP
var orders = context.Orders.ToList();

Optimizing Queries:

Use explicit Include when eager loading related entities to avoid multiple queries.
Minimize the use of Select and Where in a way that could trigger unnecessary client-side processing.

Reviewing Generated SQL:

Analyze the captured SQL for inefficiencies such as redundant joins, large result sets, or complex WHERE clauses.

#### Cons
ider indexing strategies to speed up database queries if necessary.

#### Closing Summary

Profiling and understanding the SQL generated by EF Core requires a combination of runtime diagnostics and strategic coding practices. By setting up logging, using profiling tools, identifying client-side evaluations, and optimizing queries, we can ensure that our application performs efficiently while maintaining clear and maintainable code.

#### Common Mistakes/Follow-Ups

Mistake: Overusing lazy loading without considering its impact on performance.

#### Follow-Up
Implement eager loading (Include) where necessary to reduce the number of database hits.

Mistake: Forgetting to review the SQL logs for inefficiencies.

#### Follow-Up
Regularly audit query execution plans and optimize them as needed.
