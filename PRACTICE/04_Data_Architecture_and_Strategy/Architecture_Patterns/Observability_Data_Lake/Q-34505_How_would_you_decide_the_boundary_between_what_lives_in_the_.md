# How would you decide the boundary between what lives in the observability lake versus what stays in purpose-built systems like a TSDB APM and SIEM at org scale?

**Difficulty:** Deep · **Levels:** Architect/Principal, SDE-2/3 · [↑ In-lake vs External Inference](<../../../../04_Data_Architecture_and_Strategy/Architecture_Patterns/Observability_Data_Lake/In-lake_vs_External_Inference.md>)

## Answer

To determine the boundary between data stored in an Observability Data Lake and purpose-built systems such as a Time Series Database (TSDB), Application Performance Management (APM) tool, and Security Information and Event Management (SIEM), we need to consider several factors. This decision involves balancing storage efficiency, query performance, data lineage, and compliance requirements.

#### Triaging the Question

The interviewer is probing into understanding how to architect a scalable observability system that integrates different tools while maintaining optimal data management practices. We'll need to make trade-offs between centralized storage (Observability Data Lake) and specialized systems optimized for specific use cases.

#### Assumptions
The organization has multiple applications, services, and infrastructure components.
There are different teams with varying needs for monitoring and alerting.
Compliance requirements dictate how data must be stored and accessed.

#### First-Principles Solution
Data Classification: Categorize the types of data generated by various sources (e.g., logs, metrics, traces) based on their nature and purpose.
Query Patterns: Analyze the query patterns for each type of data to understand how frequently it is accessed and its historical value.
Storage Requirements: Consider the storage requirements for different data types, including retention periods and performance needs.
Compliance and Security: Ensure that sensitive or regulated data is stored in a compliant manner.
Step-by-Step Solution

Data Classification:

Logs: Typically generated in large volumes and used for troubleshooting and post-mortem analysis. Historical logs are valuable but not frequently queried.
Metrics: Real-time performance metrics from APM tools, often time-series data with high cardinality. Requires quick query access.
Traces: Used to understand the flow of requests across services. Rarely queried historically but critical for root cause analysis.

Query Patterns:

Logs: Can be queried using complex search patterns and full-text searches, which may not perform well in a time-series database.
Metrics: Require fast time-based queries to detect anomalies and trends.
Traces: Often require correlated queries across multiple services.

Storage Requirements:

Logs: Can be stored in the Observability Data Lake with efficient indexing for full-text searches, but may have different retention policies compared to metrics.
Metrics: Ideal for storage in a TSDB where time-based queries can be performed quickly and efficiently.
Traces: Can also be stored in the Observability Data Lake initially, then moved to a TSDB with appropriate indexing.

Compliance and Security:

Sensitive data (e.g., personally identifiable information) should be handled according to compliance requirements, often necessitating storage in purpose-built systems.
Non-sensitive data can be stored in the Observability Data Lake with proper security measures in place.

#### Closing Summary

By classifying data based on its nature and query patterns, analyzing storage needs, and considering compliance requirements, we can determine an effective boundary between what should reside in the Observability Data Lake versus purpose-built systems. This approach ensures efficient data management while meeting operational and regulatory demands.

#### Common Mistakes/Follow-Ups
Over-centralization: Not recognizing that some specialized tools offer significant advantages over general-purpose solutions.
Ignoring Compliance: Failing to consider the legal and security implications of storing sensitive data in a less secure environment.
Inadequate Scalability: Designing systems without considering future growth, which can lead to performance bottlenecks.
Triaging

The key is to strike a balance between flexibility (Observability Data Lake) and specialization (APM, SIEM). By understanding the unique requirements of each system, we can create an architecture that maximizes efficiency and effectiveness.
