# Walk me through a production incident where a denormalized copy drifted out of sync with its source of truth and how you detected and reconciled it.

**Difficulty:** Deep · **Levels:** Architect/Principal, SDE-1, SDE-1/2, SDE-2/3 · [↑ Denormalization Trade-offs and Patterns](<../../../../01_Databases_and_SQL/Database_Design/Normalization/Denormalization_Trade-offs_and_Patterns/_index.md>)

## Answer

In a complex database environment, denormalization is often used to optimize read performance or reduce joins in queries. However, maintaining consistency between a denormalized copy and its source of truth can be challenging, leading to potential data discrepancies that must be carefully managed. One such incident occurred in our production environment where a denormalized copy drifted out of sync with its source.

#### Triage

The question is asking us to walk through an actual production incident involving the synchronization issues between a denormalized database and its normalized source of truth. The key points the interviewer will be probing include:

Understanding of when and why denormalization is used.
How drift can occur in a denormalized copy.
Techniques for detecting such discrepancies.
Strategies to resolve these issues without causing further data inconsistencies.

#### First Principles Solution
Understanding the Incident:
A denormalized database was created to improve read performance on frequently accessed queries, but it drifted out of sync with its normalized source.
Detecting the Drift:
We identified drift through a routine integrity check that compared key fields between the source and denormalized copy.
Analyzing the Causes:
The root cause was determined to be a recent change in data ingestion logic for the source database, which had not been reflected in the denormalization process.
Reconciliation Steps:
We reconciled the data by applying an update script based on the last known good state from the source.
Ensured all future updates were consistently applied to both databases.

#### Solution
Breakdown

Background Context: In our application, a denormalized database was created to handle frequent read operations and reduce join overhead. The normalized source of truth stored detailed transactional data, while the denormalized copy provided pre-aggregated and summarized metrics for reporting.

Incident Detection: Our automated integrity check system flagged a discrepancy in key fields between the two databases during routine monitoring. Specifically, certain aggregated values did not match their expected computed counterparts.

Root Cause Analysis: After investigating recent changes to our data ingestion pipelines, we found that an update had modified how transactional data was being stored without updating the denormalization logic accordingly. This led to a mismatch in the summarized metrics generated by the denormalized copy.

Reconciliation Plan:

We generated a script to reconcile the source and denormalized databases based on the latest known good state.
Applied this script to ensure both databases were consistent again.
Implemented additional monitoring to catch future discrepancies early.

Preventive Measures:

Enhanced our CI/CD pipelines to include automated checks for consistency between normalized and denormalized data.
Added more detailed logging and auditing around changes in data ingestion processes.

#### Closing Summary

By understanding the nuances of denormalization, detecting drift through consistent integrity checks, and implementing robust reconciliation strategies, we effectively resolved the issue. This experience highlights the importance of maintaining a clear lineage between source and derived data to prevent such incidents.

**Code:**

```sql
-- Example of a reconciliation script

-- Identify discrepancies between source and denormalized copy
WITH source_data AS (
    SELECT user_id, SUM(amount) as total_amount
    FROM transactions
    GROUP BY user_id
),
denormalized_copy AS (
    SELECT user_id, total_spent
    FROM denormalized_user_metrics
)

SELECT sd.user_id, sd.total_amount, dc.total_spent
FROM source_data sd
JOIN denormalized_copy dc ON sd.user_id = dc.user_id
WHERE sd.total_amount != dc.total_spent;
```
