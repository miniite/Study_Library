# An interviewer probes: 'why is there a composite unique constraint here instead of a single PK?' — how do you justify a natural composite uniqueness alongside a surrogate key?

**Difficulty:** Intermediate · **Levels:** SDE-1, SDE-1/2 · [↑ Surrogate vs Natural Keys for Lookups](<../../../../01_Databases_and_SQL/Database_Design/Schema_Design/Surrogate_vs_Natural_Keys_for_Lookups.md>)

## Answer

When designing a database schema, the choice between using a composite primary key (PK) and a composite unique constraint often comes down to business requirements, normalization considerations, and performance implications. In this scenario, we are asked about justifying a natural composite uniqueness alongside a surrogate key in an ER diagram.

#### Triage

The interviewer is probing your understanding of database design principles, specifically the trade-offs between using natural keys (composite or single) and surrogate keys. The core question is whether having both a natural composite unique constraint and a surrogate primary key makes sense within the context of the application requirements and constraints.

#### First-Principles Solution
1. Understanding the Scenario

In database design, we often face scenarios where data requires more than one column to uniquely identify a record. For example, in an order management system, an Order can have multiple LineItems, each with a unique combination of OrderID and ItemID.

2. Natural Composite Unique Constraint

A composite unique constraint ensures that no two records can have the same combination of columns. This is useful when natural keys are well-defined and provide semantic meaning.

SQL
CREATE TABLE LineItem (
    OrderID INT,
    ItemID INT,
    Quantity INT,
    PRIMARY KEY (OrderID, ItemID),
    UNIQUE (OrderID, ItemID)
);
3. Surrogate Key

A surrogate key is a synthetic ID generated by the database for each record. It is often used to improve performance and simplify joins.

SQL
CREATE TABLE LineItem (
    LineItemID INT PRIMARY KEY,
    OrderID INT,
    ItemID INT,
    Quantity INT,
    FOREIGN KEY (OrderID, ItemID) REFERENCES Order(OrderID, ItemID)
);
4. Justification for Both
Semantic Meaning: A composite unique constraint ensures that the combination of OrderID and ItemID uniquely identifies each line item.

#### Performance Considerations
Using a surrogate key as a primary key can improve join performance, especially in large datasets where full row lookups are more expensive.
5. Example Use Case

#### Cons
ider an e-commerce platform where orders may have the same items multiple times but with different quantities. Each OrderID and ItemID combination must be unique to avoid double-counting.

SQL
CREATE TABLE LineItem (
    LineItemID INT PRIMARY KEY,
    OrderID INT,
    ItemID INT,
    Quantity INT,
    UNIQUE (OrderID, ItemID)
);

#### Closing Summary

In summary, using both a composite unique constraint and a surrogate key is justified in scenarios where natural keys provide semantic value but performance benefits from synthetic keys are needed. This approach ensures data integrity while optimizing query performance.

#### Common Mistakes/Follow-Ups
Mistake: Ignoring the business context and treating all entities with single-column primary keys.

#### Follow-Up
Discussing edge cases, such as when a composite unique constraint might be too restrictive or when a natural key is not suitable due to data constraints.
