# How would you store hybrid-search data so you can combine a SQL full-text (keyword) score with a vector similarity score for reranking?

**Difficulty:** Deep · **Levels:** Fresher, SDE-1/2, SDE-2/3 · [↑ Vector Similarity in SQL](<../../../../01_Databases_and_SQL/SQL_Language/SQL_Fundamentals/Vector_Similarity_in_SQL.md>)

> ⚠️ Practice answer, not verified. Some answers contain mistakes; when in doubt, follow the lesson.

## Answer

To store hybrid-search data efficiently, we need to combine keyword-based search scores from full-text queries and vector similarity scores from machine learning models. The goal is to maintain performance while supporting both query types seamlessly.

#### Triage

The core issue here is how to integrate two different score systems—full-text search (FTS) which relies on keyword matching and vector similarity scores—which often come from embeddings generated by language models. We need a schema that can store the results of both scoring methods in a way that allows for efficient retrieval and combination during query execution.

#### Assumptions
The full-text score is derived from keyword matches.
The vector similarity score comes from precomputed embeddings or online similarity calculations.
Both scores are stored alongside relevant document IDs to enable quick lookups.

#### First Principles Solution
Document Storage: Each document should have a unique identifier and metadata that includes the text content for full-text search.
Full-Text Search Score: Store this score in a column or separate table, linked by document ID.
Vector Similarity Score: Embeddings can be stored as vectors in a database like PostgreSQL with support for vector similarity queries, or they can be managed externally and queried on-the-fly.
Combination Logic: During query execution, combine the full-text score and vector similarity score to rank results.

#### Implementation
Steps:

Database Schema:

Document table: Contains document ID, text content, and FTS score.
SQL
CREATE TABLE documents (
    id SERIAL PRIMARY KEY,
    content TEXT NOT NULL,
    fts_score DECIMAL(5, 2) DEFAULT 0
);
Embeddings table (optional): Stores embeddings for fast similarity lookup.
SQL
CREATE TABLE embeddings (
    doc_id INT REFERENCES documents(id),
    embedding_vector BYTEA,
    PRIMARY KEY(doc_id)
);

Indexing:

Full-text search index: Use PostgreSQL’s tsvector type and GiST or SP-GiST indexes for efficient keyword searches.
SQL
CREATE INDEX idx_documents_fts ON documents USING gin(to_tsvector('english', content));
Vector similarity index: If using a vector database, ensure it supports efficient search operations.

Query Execution:

Combine scores during query execution to rank results.
SQL
WITH fts_scores AS (
    SELECT id, setweight(to_tsvector(content), 'A') @@ to_tsquery('english', 'search_term') as score
    FROM documents
)
SELECT d.id, (fts_score + similarity_score) as total_score
FROM documents d
JOIN fts_scores fs ON d.id = fs.id
LEFT JOIN embeddings e ON d.id = e.doc_id
-- Fetch vector similarity scores if needed
ORDER BY total_score DESC;

#### Closing Summary

By integrating full-text search and vector similarity into a single schema, we ensure that both types of queries can be executed efficiently. The key is to store the necessary metadata separately and combine them during query execution.

#### Common Mistakes
& Follow-Ups:
Mistake 1: Not properly indexing the full-text column, leading to slow search performance.

#### Follow-Up
Ensure that the to_tsvector and @@ operators are used correctly for efficient keyword matching.
Mistake 2: Ignoring vector similarity storage or querying complexity.

#### Follow-Up
Consider using a specialized vector database (e.g., Milvus) if the vectors are large, or handle them on-the-fly with a join operation.
