# How does partition pruning work, and how would you confirm from an execution plan that only the intended partitions were scanned?

**Difficulty:** Intermediate · **Levels:** Architect/Principal, SDE-1, SDE-1/2, SDE-2/3 · [↑ Partition Pruning](<../../../../01_Databases_and_SQL/Database_Operations/Partitioning/Partition_Pruning/_index.md>)

## Answer

Partition pruning is a critical optimization technique in database systems where a query can be executed more efficiently by scanning only relevant partitions of a table, rather than the entire table. This process significantly reduces I/O operations and improves overall performance. In this answer, we'll explore how partition pruning works, specifically with range partitioning, and demonstrate how to confirm that only the intended partitions are scanned using an execution plan.

#### Triaging the Question

The core of this question revolves around understanding the mechanisms behind partition pruning and verifying its correctness through an execution plan. The interviewer is probing your knowledge of database optimization techniques and your ability to interpret query plans effectively. Assumptions include a basic understanding of SQL, familiarity with common database management systems (DBMS), and experience with partitioning strategies.

#### First-Principles Solution

Partition pruning works by dividing a large table into smaller, more manageable pieces based on specific criteria—such as range values, hash functions, or list values. When a query is executed, the DBMS identifies which partitions are relevant to the query's conditions and processes only those partitions, skipping irrelevant ones.

For example, in a range partitioned table where data is divided by date ranges (e.g., customer_orders by year), if a query filters orders from 2019, only the partitions corresponding to that year will be scanned. This ensures that the DBMS does not waste resources on unnecessary data.

To confirm that partition pruning has been applied correctly, we can inspect the execution plan generated by the DBMS. The execution plan should indicate which specific partitions are being accessed and processed, allowing us to validate that only the intended partitions are scanned.

Confirming Partition Pruning with an Execution Plan

Let's walk through a practical example using a range partitioned table:

Scenario Setup

#### Cons
ider a customer_orders table partitioned by year:

SQL
CREATE TABLE customer_orders (
    order_id INT,
    customer_id INT,
    order_date DATE,
    amount DECIMAL(10, 2)
) PARTITION BY RANGE (YEAR(order_date)) (
    PARTITION p2018 VALUES LESS THAN (2019),
    PARTITION p2019 VALUES LESS THAN (2020),
    PARTITION p2020 VALUES LESS THAN (2021),
    PARTITION p2021 VALUES LESS THAN MAXVALUE
);
Query and Execution Plan Analysis

Let's assume we run the following query to find all orders from 2019:

SQL
SELECT * FROM customer_orders WHERE order_date BETWEEN '2019-01-01' AND '2019-12-31';
Analyzing the Execution Plan

To analyze the execution plan, we can use the EXPLAIN command (or equivalent) in our DBMS. Here is an example using PostgreSQL:

SQL
EXPLAIN SELECT * FROM customer_orders WHERE order_date BETWEEN '2019-01-01' AND '2019-12-31';

The output might look like this:

CODE
 QUERY PLAN
-------------------------------------------------------------------------
 Index Scan using customer_orders_order_date_index on customer_orders  (cost=0.56..47.89 rows=1000 width=25)
   Recheck Cond: ('2019-01-01' <= order_date AND order_date < '2020-01-01')
 Planning Time: 0.343 ms
 Execution Time: 0.124 ms

Notice that the query plan mentions Index Scan using customer_orders_order_date_index. This indicates that only partitions relevant to the year 2019 are being accessed.

Key Points from the Plan:
The plan shows which index or partition is being scanned.
It explicitly states the range of values being considered, confirming that other partitions (e.g., 2018 and 2020) are not involved in the query execution.

#### Closing Summary
and Common Mistakes

Partition pruning effectively reduces the data volume processed by a query, leading to improved performance. To ensure partition pruning is working as intended:

Verify the execution plan shows only relevant partitions being scanned.
Ensure that your index or partitioning strategy supports efficient range queries. Common mistakes include not properly defining partition boundaries, which can lead to unnecessary scans across multiple partitions.
