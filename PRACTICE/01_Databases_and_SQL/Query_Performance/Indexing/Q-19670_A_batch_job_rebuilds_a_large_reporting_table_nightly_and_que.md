# A batch job rebuilds a large reporting table nightly and query latency spikes for the first hour after. How do you tie that to stale statistics or a cold cache and fix it durably?

**Difficulty:** Deep · **Levels:** Architect/Principal, SDE-1/2, SDE-2/3 · [↑ Index Tuning in Practice](<../../../../01_Databases_and_SQL/Query_Performance/Indexing/Index_Tuning_in_Practice/_index.md>)

## Answer

To address the issue of increased query latency during the initial hour following a nightly rebuild of a large reporting table, we need to investigate whether the problem stems from stale statistics or a cold cache, and then implement durable solutions. Let's start by breaking down the key aspects of the problem.

Triaging the Issue

The core question is whether the performance bottleneck is due to outdated query statistics (cost-based optimization) or a caching issue that leads to suboptimal execution plans being used initially. We need to understand the interaction between the database indexing and query execution, especially in the context of frequent schema changes and subsequent cache invalidation.

#### Assumptions
The nightly rebuild process is deterministic and follows a consistent pattern.
The reporting table contains large volumes of data, making it prone to performance issues if not managed correctly.
The queries run against this table are complex and possibly use indexes in ways that could be suboptimal without up-to-date statistics.

#### First-Principles Solution
Analyze Query Execution Plans: Examine the query execution plans generated by the database before and after the nightly rebuild to identify any changes in how the queries are being executed.
Check Statistics Validity: Ensure that the statistical information used by the cost-based optimizer is up-to-date. This involves verifying if the statistics have been updated post-rebuild.
Assess Cache Usage: Determine whether a cache (e.g., query plan cache, result set cache) might be holding onto suboptimal plans from before the rebuild.
Step-by-Step Solution

Review Query Execution Plans:

Use the database’s built-in tools or third-party utilities to capture execution plans for key queries.
Compare these plans against those generated on a different day (preferably after no recent schema changes) to detect any anomalies.

Check Statistics Validity:

Ensure that statistics are collected and updated post-rebuild. For PostgreSQL, you can use ANALYZE or EXPLAIN ANALYZE to force an update.
Check the pg_statistic system catalog to verify if statistics have been updated.

Assess Cache Usage:

Identify which caches might be relevant (e.g., query plan cache in PostgreSQL, in-memory data stores).
Invalidate or refresh these caches post-rebuild to ensure they contain the latest and most efficient plans.
Durable Solutions
Automate Statistics Updates: Implement a routine that runs ANALYZE after the nightly rebuild process is complete.
Cache Management Policies: Define policies for cache invalidation and revalidation. For example, in PostgreSQL, you can use pg_statistic to monitor when statistics are outdated and automatically invalidate relevant plans.

#### Closing Summary

By tying down the issue to either stale statistics or a cold cache, we can implement durable solutions that maintain optimal query performance over time. Ensuring that statistics are updated post-rebuild and managing cache invalidation policies will mitigate the initial latency spike experienced during the first hour after the nightly rebuild.

#### Common Mistakes/Follow-Ups
Failing to Update Statistics: Not running ANALYZE or EXPLAIN ANALYZE can lead to suboptimal query plans.
Over-relying on Caches: If caches are not invalidated properly, stale execution plans can cause prolonged performance issues.
