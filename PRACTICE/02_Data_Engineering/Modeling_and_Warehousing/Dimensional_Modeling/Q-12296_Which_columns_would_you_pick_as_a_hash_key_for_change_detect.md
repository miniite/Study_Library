# Which columns would you pick as a hash key for change detection in an SCD Type 2 load, and how do you handle NULLs and column additions in the hash?

**Difficulty:** Deep · **Levels:** Architect/Principal, SDE-1, SDE-1/2, SDE-2/3 · [↑ SCD Type 2 vs Mini-dimensions](<../../../../02_Data_Engineering/Modeling_and_Warehousing/Dimensional_Modeling/SCD_Type_2_vs_Mini-dimensions.md>)

## Answer

When dealing with Slowly Changing Dimension (SCD) Type 2 data, particularly in an environment where change detection is critical, selecting appropriate columns as a hash key is crucial. For this discussion, we'll focus on identifying the best candidates and how to handle NULLs and column additions.

#### Triaging the Question

The core of the question revolves around:

Choosing Appropriate Columns for Hash Keys: These should be stable and unique identifiers.
Handling NULLs in Hash Keys: Ensuring that NULL values don't skew or invalidate hash calculations.
Managing Column Additions: Ensuring new columns are properly integrated into existing data models without disrupting the integrity of historical records.
Core Solution

For SCD Type 2, we typically use a combination of surrogate keys and natural keys as part of our hash key strategy. The primary goal is to ensure that even minor changes in non-identifier columns do not affect the hash value too significantly. Let's break down the steps:

Identify Primary Keys: These are unique identifiers for each record.
Select Stable Columns: Choose columns that rarely change or have minimal impact on the overall data distribution.
Handle NULLs: Ensure that NULL values do not cause issues by either converting them to a known value (e.g., NULL to an empty string) or using a placeholder.
Column Additions: When new columns are added, update the hash key calculation logic accordingly.

#### First-Principles Solution
Primary Key Selection:
Use the surrogate primary key generated by your system (e.g., ORDER_ID).
Stable Columns for Hash Key:
Include columns like CUSTOMER_NUMBER, ORDER_DATE, and PRODUCT_CODE.
Handling NULLs:
Replace all NULL values with a consistent string or integer, such as 0 or 'NULL'.
Sample Data Schema
PLAINTEXT
CREATE TABLE Orders (
    ORDER_ID INT PRIMARY KEY,
    CUSTOMER_NUMBER VARCHAR(255),
    ORDER_DATE DATE,
    PRODUCT_CODE VARCHAR(255),
    ORDER_TOTAL DECIMAL(10, 2)
);
Hash Key Calculation Example

Using a simple hash function based on the selected columns:

SQL
CREATE OR REPLACE FUNCTION calculate_hash_key(order_id INT, customer_number VARCHAR(255), order_date DATE, product_code VARCHAR(255)) RETURNS VARCHAR(36) AS $$
BEGIN
    RETURN MD5(
        ORDER_ID::TEXT ||
        COALESCE(CUSTOMER_NUMBER, 'NULL') ||
        TO_CHAR(ORDER_DATE, 'YYYY-MM-DD') ||
        COALESCE(PRODUCT_CODE, 'NULL')
    );
END;
$$ LANGUAGE plpgsql;
Managing Column Additions
Identify New Columns: For example, a new column SHIPPING_ADDRESS.
Update Hash Key Calculation:
Extend the hash function to include this new column.
Updated Hash Function

#### Closing Summary
and Common Mistakes
Common Mistake 1: Overlooking NULL values in hash key columns.
Common Mistake 2: Ignoring the impact of new column additions on existing records.
Best Practice: Regularly review and update your hash functions as schema changes occur.
