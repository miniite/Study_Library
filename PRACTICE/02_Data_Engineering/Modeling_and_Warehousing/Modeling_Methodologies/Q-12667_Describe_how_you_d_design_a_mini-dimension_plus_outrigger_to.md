# Describe how you'd design a mini-dimension plus outrigger to control SCD Type 2 growth for a customer demographics attribute set, and when it's overengineering.

**Difficulty:** Deep · **Levels:** Architect/Principal, SDE-2/3 · [↑ Data Vault](<../../../../02_Data_Engineering/Modeling_and_Warehousing/Modeling_Methodologies/Data_Vault.md>)

## Answer

#### Overview
When designing data models in a real-world context, especially with complex attributes like customer demographics, we often encounter the need to manage historical changes effectively. In this scenario, we will design a mini-dimension plus an outrigger schema to handle SCD Type 2 (Slowly Changing Dimension Type 2) growth for a customer demographic attribute set, while considering whether it is overengineering.

#### Triage
The question aims to assess your understanding of data modeling principles and your ability to apply them in practical scenarios. Specifically, the interviewer wants to know how you would structure a dimension table that handles historical changes (SCD Type 2) for attributes like customer demographics, and whether adding an outrigger schema is necessary or overengineered.

#### Assumptions

The customer demographic attribute set includes fields such as age range, income level, and marital status.
We are using Kimball's data warehousing methodology with a focus on the Star Schema approach.
Historical changes in these attributes need to be tracked for reporting purposes.
The primary key of the dimension is a surrogate key.

#### First-Principles Solution

Designing the Mini-Dimension Table:

Create a base mini-dimension table that captures the current state of customer demographics.
Include columns such as DimCustomerDemographicID, AgeRange, IncomeLevel, and MaritalStatus.

Adding SCD Type 2 Columns:

To handle historical changes, add columns like EffectiveStartDate and EndDate to the mini-dimension table.
These columns will track when a demographic change was effective and when it expired.

Creating an Outrigger Table:

The outrigger table is used to capture historical versions of the dimension values.
It should have a structure similar to the base table but with surrogate keys for each version.
Columns in this outrigger table include DimCustomerDemographicID, AgeRange_Historical, IncomeLevel_Historical, MaritalStatus_Historical, and VersionID.

Handling Updates:

When a demographic attribute changes, insert a new row into the outrigger table with the new values and set the old value as expired.
Update the base mini-dimension table to reflect the current state by setting the EndDate of the previous version.

#### Performance Considerations

Evaluate whether the additional complexity introduced by the outrigger schema is necessary for performance.
If there are only a few updates per customer demographic attribute, this might be overengineering.

Querying Historical Data:

To retrieve historical data, join the mini-dimension table with the outrigger table using appropriate conditions on EffectiveStartDate and EndDate.

#### Closing Summary
The design of a mini-dimension plus an outrigger schema is a robust approach for handling SCD Type 2 growth in customer demographics. It ensures that historical changes are tracked accurately while maintaining performance efficiency. However, whether this is overengineering depends on the frequency of updates and the volume of data.

#### Common Mistakes/Follow-Ups

Forgetting to update the EndDate in the outrigger table when a new version is inserted.
Not considering the potential performance impact of additional joins in queries that retrieve historical data.
Overlooking the need for proper indexing on the surrogate keys and timestamp columns.

**Code:**

```sql
-- Mini-Dimension Table
CREATE TABLE DimCustomerDemographic (
    DimCustomerDemographicID INT PRIMARY KEY,
    AgeRange VARCHAR(50),
    IncomeLevel VARCHAR(50),
    MaritalStatus VARCHAR(50),
    EffectiveStartDate DATE NOT NULL DEFAULT CURRENT_DATE,
    EndDate DATE
);

-- Outrigger Table
CREATE TABLE DimCustomerDemographic_Historical (
    VersionID INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    DimCustomerDemographicID INT NOT NULL,
    AgeRange_Historical VARCHAR(50),
    IncomeLevel_Historical VARCHAR(50),
    MaritalStatus_Historical VARCHAR(50),
    EffectiveStartDate DATE NOT NULL DEFAULT CURRENT_DATE,
    EndDate DATE
);
```

**Example input / output:**

```text
-- Example of Inserting a New Demographic Attribute
INSERT INTO DimCustomerDemographic (DimCustomerDemographicID, AgeRange, IncomeLevel, MaritalStatus)
VALUES (101, '25-34', 'High', 'Single');

-- Example of Handling an Update
UPDATE DimCustomerDemographic
SET EndDate = CURRENT_DATE - INTERVAL '1 day' -- Set the old version as expired
WHERE DimCustomerDemographicID = 101 AND AgeRange = '25-34' AND IncomeLevel = 'High';

INSERT INTO DimCustomerDemographic_Historical (DimCustomerDemographicID, AgeRange_Historical, IncomeLevel_Historical, MaritalStatus_Historical)
VALUES (101, '35-44', 'Medium', 'Married');
```
