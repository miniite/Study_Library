# Why might you disable tombstone events in Debezium for a particular sink and what downstream behavior changes when you do?

**Difficulty:** Deep · **Levels:** SDE-1/2, SDE-2/3 · [↑ Debezium Transforms and Snapshots](<../../../../02_Data_Engineering/Pipelines_and_Integration/Change_Data_Capture/Debezium_Transforms_and_Snapshots.md>)

## Answer

To address the question of why you might disable tombstone events in Debezium, it's important to first understand the concept of tombstone events and their role in data streaming systems. In a nutshell, disabling tombstone events can lead to downstream applications treating deleted records differently or causing unexpected behavior, such as data skew or inconsistent state.

Tombstone events are special markers used by change data capture (CDC) tools like Debezium to indicate that a record has been logically deleted from the source system. These events typically contain information about the key of the deleted row and often have a timestamp to help maintain temporal consistency in downstream systems.

Disabling tombstone events means these logical deletions are not propagated or stored by the CDC tool, which can lead to various consequences:

Downstream Data Integrity: Without tombstone events, downstream applications might fail to clean up references to logically deleted records.
State Management: Applications relying on CDC for state management may face issues if they expect tombstones to help maintain a consistent view of the data over time.

Let's break this down from first principles:

Understanding Tombstone Events:

Tombstone events are a mechanism used by Debezium and similar tools to inform downstream systems about logical deletions in source databases.
They typically contain metadata such as the key of the deleted row, which helps maintain temporal consistency.

Why Disable Tombstone Events?:

#### Performance Considerations
Disabling tombstone events can reduce the overhead associated with emitting and processing these events, potentially improving performance.
Storage Constraints: In scenarios where storage space is limited, disabling tombstones might be a viable option to save on disk space or reduce the size of changelogs.

Downstream Behavior Changes:

Data Integrity: Without tombstone events, downstream systems may not be able to properly manage deleted records, leading to potential data skew.
State Management: Applications that rely on CDC for state management might face issues if they expect tombstones to help maintain a consistent view of the data over time.

#### Example Scenario

#### Cons
ider an application using Debezium to replicate changes from a source database into a downstream analytics platform. If tombstone events are disabled, the analytics platform may not receive signals about deleted records, leading to inconsistent state and potential errors when querying historical data.

Best Practices:

While disabling tombstone events can be beneficial in certain scenarios, it's crucial to weigh the trade-offs carefully.
Ensure that any downstream systems capable of handling logical deletions are aware of this decision to avoid data integrity issues.

In summary, while disabling tombstone events in Debezium can offer performance benefits or storage optimizations, it introduces risks related to data integrity and state management. Careful consideration should be given to the specific requirements and constraints of your system before making such a decision.
